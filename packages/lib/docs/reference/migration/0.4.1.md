# Upgrading from 0.4.0 to 0.4.1

## Closing a tab now destroys its content

**What changed and why.** A closed tab's content, and everything below it, is
now disposed. Before, nothing was — `Tab.closeEntry` (the single close
implementation behind the ✕ click, the context menu's close items, and
`Tab.closeTab`) only detached the content, and the same gap existed for
`TabBar`'s own strip-cell button and for a dismissed `Notification`. Every
per-instance stylesheet rule the closed subtree had allocated stayed on the
shared sheet for the life of the page, and style recalculation cost grows
with the size of that sheet — a long session of tab churn degraded.

**Who needs to act.** Nobody who discards a closed tab's content, which is
the normal case — that content is now torn down for you instead of leaking.
Action is needed only where a component is deliberately re-used after its
tab closes.

**The three opt-out spellings**, all defaulting to destroy:

- `LayoutConstraints.disposeOnClose: false` — the per-child constraint, for a
  bare `Container` + `Tab` consumer.
- `DockPanelSpec.disposeOnClose: false` — for a `Dock` panel.
- `TabPanel.addTab(component, label, { disposeOnClose: false })` — also
  accepted on a `TabPanel`'s `tabs` config entries and `addLazyTab`.

A `"tabclose"` listener that re-parents the content (`otherContainer.moveComponent(content)`)
keeps it alive too, with no flag needed — it has an owner again by the time
the destroy check runs. The opt-out survives a `getLayoutState()` /
`setLayoutState()` round trip: `LayoutSerialization`'s `PanelNode` now
captures `disposeOnClose` (and `tooltip` / `closeable`) alongside the
existing `glyph`, so a restored tab keeps the behaviour it was registered
with instead of silently reverting to the destroy default.

**The `Dock` case worth checking.** A `DockPanelSpec` whose `content` is a
**live component** that you re-add after a close needs
`disposeOnClose: false`. A spec whose `content` is a **factory** needs
nothing — a re-add rebuilds through it.

**What a consumer's own disposal registry can now delete.** Any registry
that existed only to dispose a panel when its tab closed is dead code now —
including the flag that gated it, the per-panel `register` call, and any
in-flight-build token pair used to recognise (and drop) a component that
finished building after its tab was already closed. That in-flight case is
covered by the library: closing a tab cancels that tab's materialization,
and the materialize helper then disposes the component the factory later
produces instead of mounting it, so nothing arrives unowned and no token is
needed.

**What stays the consumer's job, and where it must live.** Releasing a
resource the panel owns — terminating a worker, closing a socket, clearing
an interval — is still application code. It belongs in a
`protected destructor()` override on the panel's `Component` subclass,
ending in `super.destructor()` — never in a `dispose()` method the framework
has no way to call.

**The wrapper trap, stated in full.** Teardown recursion calls `destructor()`
on each registered child. A `dispose()` **method or arrow-field on a plain
object that wraps a `Component`** is therefore never reached — the wrapper
is not in any parent's child list, and even a `dispose()` on a `Component`
subclass is not what the recursion calls. Audit every composition wrapper
that declares `dispose`: either move its body into a `protected destructor()`
override on a `Component` subclass, or have an owning `Component`'s
`destructor()` call the wrapper explicitly. An empty or no-op `dispose` on
such a wrapper is the signal that cleanup was never wired at all.
