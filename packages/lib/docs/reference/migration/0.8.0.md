# Upgrading from 0.7.0 to 0.8.0

## `ComponentOptions.styleGroup` is removed

**What changed and why.** `ComponentOptions.styleGroup` (with
`setStyleGroup`/`getStyleGroup`) let several instances of one concrete class
share a single generated `.ClassName--<token>` CSS rule, with whichever
instance in the group rendered first fixing the shared content. Nothing in
the library used it any more — its last consumer, a table header's
column-menu button, now declares its icon size as a shared `StyleTrait`
instead (see the new cross-class style trait tier in this release's Added
notes), which publishes one rule for every owner regardless of render
order. The option, both accessors, and the `.ClassName--<token>` DOM class
and CSS rule they generated are all gone. This is a deliberate pre-1.0 cut
of an unused mechanism, not a drop-in replacement.

**Who needs to act.** Any call to `new Foo({ styleGroup: ... })`,
`setStyleGroup(...)`, or `getStyleGroup()` is now a compile error. For
instances of one class that should look alike regardless of render order,
declare a `StyleTrait` — a plain `{ name, declarations }` bag — and opt in
via the new `styleTrait` construction option or `setStyleTrait`:

```typescript
const HIGHLIGHT: StyleTrait = {
    name: "highlight",
    declarations: { backgroundColor: "yellow" },
};

new Button({ styleTrait: HIGHLIGHT, ... });
```

Every owner of the same `StyleTrait` object shares one CSS rule, published
from the trait's own fixed `declarations` rather than from whichever
instance renders first. Alternatively, give the shared look its own
subclass with its own class defaults. A consumer stylesheet selector
targeting a generated `.ClassName--<token>` class no longer matches
anything.

## Theme `scale.titleGlyph` / `scale.tabCloseGlyph` are replaced by a five-step icon scale

**What changed and why.** The two single-purpose pixel tokens are gone,
replaced by an ordered, five-step icon scale that every framework icon now
reads instead of a hardcoded literal: `glyphXs` (8px at the default base),
`glyphSm` (12px), `glyphMd` (14px — the old `titleGlyph`'s slot), `glyphLg`
(16px, the default icon size), and `glyphXl` (20px). `tabCloseGlyph` (also
8px) maps onto the same slot as `glyphXs`. Naming the scale by size rather
than by the one call site that used to own each pixel value lets every icon
in the library — not just a window title glyph or a tab's close ✕ — share
the same five steps, so raising `scale.base` now scales all of them
together.

**Who needs to act.** A custom theme built as a full `Theme` object no
longer typechecks with `titleGlyph` / `tabCloseGlyph` in its `scale` block,
and is missing the five new required `glyph*` tokens. Replace
`scale.titleGlyph` with `scale.glyphMd`, and `scale.tabCloseGlyph` with
`scale.glyphXs` — both keep the exact same resolved size at the default
base, so nothing visually shifts from making the substitution alone. A
theme that overrode neither token needs no change beyond picking up the
library's new default `glyph*` values, which are also unchanged from the
old tokens' values in every shipped theme.

## A table's row-viewport body loses its `Body` DOM class

**What changed and why.** A `Table`'s row-viewport body element was
declared `class Body` internally, colliding with `core/Body`'s app-root
singleton (also `class Body`) in the class-tier registry's name-keyed
lookup. The singleton's eager construction always won that name, so the
table body always lost and fell back to the registry's name-collision
opt-out — repeating its full framework baseline plus `backgroundColor` on
every instance's own `#id` rule on every render, instead of sharing one
class-tier rule. The internal declaration is renamed to `TableBody` — the
name the docs already recommended importing the public export as — which
lets it join the hierarchy-aware class tier the same way `Cell`'s built-in
subclasses do. Its rendered element now additionally carries its own
ancestor's name, `VirtualRowView`. A `TreeTable`'s body keeps its own
`TreeBody` class, but likewise gains `VirtualRowView` and `TableBody`
alongside it.

**Who needs to act.** Audit any consumer stylesheet selector written
against the table body's rendered class list before upgrading:

- A selector targeting `.Body` on a `Table`'s or `TreeTable`'s row-viewport
  body — previously the only class it carried beyond `ts-ui-component` —
  no longer matches anything there.
- A selector targeting `.VirtualRowView` or `.TableBody` now matches both a
  `Table`'s and a `TreeTable`'s body, where previously neither existed.

The public export (`Body`, from `component/table/index.ts`) is unchanged —
only the rendered DOM class list changes. Nothing else about the
component's behavior or API is affected.

## `DiagramView` opens fitted to the viewport by default

**What changed and why.** `DiagramView`'s first successful centring
previously held whatever `zoom` was configured, however large or small the
graph turned out to be relative to the viewport. A new `fitOnLoad` option
now controls that first centring — fitted (the same scale and centring the
built-in Fit to view control produces) when `true`, or holding the
configured `zoom` when `false` — and it defaults to `true`, since every
consumer already fit the initial view by hand. The change applies exactly
once, to the first centring that succeeds, and only when no
`initialFocusNode` is set; a later `setData`, the off-screen re-centring
floor, and the Reset view control are all unaffected.

**Who needs to act.** A consumer relying on the previous behavior — the
view opening at the configured `zoom` regardless of graph size — must now
pass `fitOnLoad: false` explicitly:

```typescript
new DiagramView({ fitOnLoad: false, zoom: 1, ... });
```

A consumer that sets `initialFocusNode`, or that already called
`zoomToFit()` / `resetView()` by hand right after construction, needs no
change — `initialFocusNode` already wins over `fitOnLoad`, and the new
default simply does automatically what those consumers were already doing
by hand.
