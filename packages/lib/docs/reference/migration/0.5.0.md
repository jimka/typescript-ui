# Upgrading from 0.4.1 to 0.5.0

## `Theme.drawer.background` / `Theme.rail.background` removed

**What changed and why.** Both tokens were set to `'var(--ts-ui-body-bg)'` in
every shipped theme — a redundant alias with no per-theme value of its own.
`Drawer` and `Rail` now read `--ts-ui-body-bg` directly instead, the same
pattern `AbstractWindow` and `Dialog` already used. The rendered colour is
unchanged in every shipped theme.

**Who needs to act.** Only a custom theme that set `drawer.background` or
`rail.background` to something *other* than `--ts-ui-body-bg`. That override
is now silently lost — `Drawer`/`Rail` fall back to the body background
instead. Reapply the intended colour per instance instead, via
`Component.setBackgroundColor` on the `Drawer` / `Rail` in question.

## Component options that were silently ignored now take effect

**What changed and why.** A cluster of components accepted certain
constructor options but discarded them after construction and always painted
a hardcoded default instead — a "clobbering" bug fixed across several sweeps
this release. Every one of these now honours the option as documented:

- **`backgroundColor`** (and, on `StatusBar`, `SortPriorityBadge`, and
  `Popover`, `foregroundColor`) — on `Tree`, `MenuBar`, `DiagramNode`,
  `DiagramGroupNode`, `ScrollStrip`, `TabButton`, `StatusBar`, `TabBar`,
  `MenuSeparator`, `SortPriorityBadge`, `Scrollbar`, `ToolBarSeparator`,
  `ChartLegend`, and `Popover`.
- **`border`, `borderRadius`, `shadow`, `cursor`, `outline`, `overflow`,
  `preferredSize`, `minSize`, or `maxSize`** (depending on the component) —
  on `DiagramNode`, `DiagramGroupNode`, `StatusBar`, `Popover`, `TabButton`,
  `MenuBar`, `Tree`, `TabBar`, `Checkbox`, `RadioButton`, `Toggle`, `Slider`,
  and `AbstractChart`.
- **`preferredSize`/`minSize`/`maxSize` width** — on `TextField`,
  `PasswordField`, `UsernameField`, `ComboBox`, `NumberSpinner`, and every
  `AbstractPickerField` subclass (`DateField`, `TimeField`, `DateTimeField`),
  which reasserted a hardcoded width on every construction and theme change.
  Height is still fully recomputed from the theme and remains
  non-configurable.
- **`preferredSize`/`maxSize`** alongside `orientation` on `Slider`, and
  **`border`** alongside `orientation` on `ToolBar` — both previously
  overwritten by the orientation-recompute at construction time. Calling
  `setOrientation` at runtime still recomputes the field unconditionally,
  unchanged.
- **`touchAction`** on `Scrollbar` — `init()` used to repaint
  `touchAction: "none"` after construction had already applied the option's
  value. The default resting behaviour (`touchAction: "none"`) is unchanged.

**Who needs to act.** Nobody, in the common case — passing any of the
options above simply works now instead of being ignored. Action is only
needed where code relied on the old, buggy behaviour: for example, a wrapper
that compensated for an ignored `border`/`backgroundColor` by painting its
own overlay, or a test asserting the old hardcoded default.

## `Button`'s `flat: true` no longer falls through to the browser's default face

**What changed and why.** `Button` painted its resting background with a
hardcoded token instead of a class default, so a `flat: true` button fell
through to the browser's native `<button>` face instead of rendering
transparent. The token is now a proper class default, so `flat: true` now
correctly renders a transparent resting background. The same fix makes
`TabButton` honour a caller-supplied `hoverBackgroundColor`,
`hoverBackgroundImage`, `hoverShadow`, and `hoverBorder`, and `MenuBarButton`
honour `insets` and `chromeless` — all six were previously discarded.

**Who needs to act.** Only code using `flat: true` that depended on the old
browser-default button face. Every other button's default appearance is
unchanged.
