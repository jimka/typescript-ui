# Upgrading from 0.10.0 to 0.11.0

## A `Window` or `TabWindow` takes focus when it is shown

**What changed and why.** A shown window was announced by a screen reader
only when focus happened to enter it. `show()` now moves focus to the window
after its first layout; `bringToFront()` moves it at once, also when the window
is already the active one; closing a window that took focus returns focus to
the element it took it from. Pass `autoFocus: false` to a window that should not
take focus.

| Call | Before | Now |
| --- | --- | --- |
| `win.show()` | focus stays on the opener | focus moves to the window |
| `win.bringToFront()` on the active window | focus stays | focus moves to the window |
| closing a window that took focus | focus on `<body>` | focus on the element it took focus from |

A window takes focus only when focus is outside it. When the application
focuses a field inside the window right after `show()`, the window has taken
nothing, and closing it leaves focus on `<body>`, as before.

**Who needs to act.** Code that shows a window while the user keeps working
elsewhere: a tool palette, a log or status window, a window opened from a
timer or a network reply. Build it with `autoFocus: false`. Code that focuses
its own field right after `show()` needs no change, because focus arrives
after the window's first layout.

`autoFocus: false` opts a window out of the new focus moves; it does not
bring back every old behaviour.

| Call | Before | With `autoFocus: false` |
| --- | --- | --- |
| `win.show()` | focus stays on the opener | focus stays on the opener |
| `win.bringToFront()` on the active window | focus stays | focus stays |
| `win.bringToFront()` on an inactive window | focus moves to the window | focus stays |
| a press inside an inactive window, or `restore()` | focus moves to the window | focus moves to the window |
| closing a window that holds focus | focus on `<body>` | focus on the element it took focus from, when a press or `restore()` moved it in; otherwise on `<body>` |

```typescript
// Before
new Window("Log").show();               // focus stayed where it was

// After — keep it out of the way
new Window("Log", { autoFocus: false }).show();
```

## A restore that interrupts a rail minimize fires the `minimize` it owed first

**What changed and why.** A window minimizing into a
[`Rail`](/components/Rail) shrinks into its handle over 150 ms, and its
`"minimize"` is held back until that shrink lands — so the handle appears
when the window has finished shrinking into it. A restore arriving inside
that window used to *void* the held-back event, on the ground that a window
leaving `"minimized"` has nothing left to announce. But the window's state
reads `"minimized"` for the whole shrink, so a consumer polling
`getWindowState()` saw a transition into and out of `"minimized"` that no
event ever reported, and one pairing the two events saw a `"restore"` with
no `"minimize"` before it. The debt is now paid instead of voided, which is
what [`setRail`](/api/overlay/classes/AbstractWindow#setrail) already did
for a window that stays minimized under a new owner. A restore that lets the
shrink land is unchanged, and so is a close or a dispose inside it: the first
still announces `"close"` alone, the second still announces nothing.

**Who needs to act.** Nothing fails to compile, and a consumer that only
mirrors the window's state — as `Rail` itself does — needs no change. A
listener that treated `"minimize"` as "the window is now hidden behind a rail
handle" sees one more call, for a window that is about to be shown again in
the same task; it should read `getWindowState()` in the handler, or wait for
the paired `"restore"`, rather than assume.

```typescript
// Before — a restore inside the 150 ms shrink
win.on("minimize", onMin);
win.on("restore",  onRes);
win.minimize();
win.restore();      // onRes only

// After
win.minimize();
win.restore();      // onMin, then onRes — in that order, in the same task
```

## `DOM.sink` and `DOM.source` are read-only

**What changed and why.** The two seam properties are now declared `readonly`,
so they are swapped through
[`DOM.install`](/api/core/interfaces/DOMSeams#install) or
[`DOM.reset`](/api/core/interfaces/DOMSeams#reset) and nowhere else. In 0.11.0
those two calls tell the library's seam-derived caches that the handles they
hold have stopped resolving — a `Handle` only means anything to the seam that
minted it, and `reset` rebuilds the shared handle registry outright. A direct
assignment would go around that notification and leave a cache writing
through a handle the incoming sink never minted. Making the properties
read-only makes the two swap routes the only ones, so the notification cannot
be bypassed.

**Who needs to act.** Only code that assigned a seam directly, which no
documented path ever did. The assignment is now a compile error; install the
seam instead, which is also what restores the production pair:

```typescript
// Before
DOM.sink = myRecordingSink;

// After
DOM.install({ sink: myRecordingSink });
// … and to restore the production pair
DOM.reset();
```

## `DOMSink` gains `createMouseEvent`

**What changed and why.** One more construction moved behind the seam.
`createMouseEvent(type, init)` builds a mouse event and returns it without
dispatching it. `Tree` and `List` call it for the `contextmenu` event they hand
a `"contextmenu"` listener when the menu is opened with Shift+F10 or the
ContextMenu key, so that no library code names the global `MouseEvent`
constructor.

**Who needs to act.** Only a consumer implementing its own `DOMSink`; the
missing member is a compile error. In a browser, return
`new MouseEvent(type, init)`. A sink that runs without a DOM returns a plain
object carrying `type`, the `init` fields a listener reads (`clientX`,
`clientY`, `button` and the four modifier flags, defaulting to `0` and
`false`), a `null` `target`, and no-op `preventDefault()` /
`stopPropagation()`.

```typescript
import type { DOMSink } from '@jimka/typescript-ui/core';

class MySink implements DOMSink {
    // …
    createMouseEvent(type: string, init: MouseEventInit): MouseEvent {
        return new MouseEvent(type, init);
    }
}
```

## A keyboard `"contextmenu"` event on a `Tree` or `List` has a `null` target

**What changed and why.** Shift+F10 and the ContextMenu key now open the
context menu of the current row. The browser sends the key's event to the
widget's own element and not to a row, so the widget hands its
`"contextmenu"` listener a synthetic event positioned under the current row.
That event has not been dispatched, so its `target` is `null`. In 0.10.0 the
listener ran only for a right-click on a row, whose `target` is inside that
row.

**Who needs to act.** A `Tree`, `List` or `MultiSelectList` `"contextmenu"`
listener that reads `event.target`. Use the node or index the listener
receives and `clientX` / `clientY`, which are set in both cases:

```typescript
tree.on("contextmenu", (node, event) => {
    menu.show(event.clientX, event.clientY, itemsFor(node));
});
```

## A `Panel` subclass that scrolls something of its own overrides `revealRect`

**What changed and why.** `FocusReveal.reveal` no longer calls
`revealDescendant(target)` on a scrolling panel. With panels inside one
another that call made each panel measure the control for itself, the
outermost first, and the control could end out of view. The broker now
measures the control once and hands the rectangle from panel to panel, the
innermost first, through `revealRect(rect, axis?)`: each panel scrolls to show
the rectangle it is handed and returns what it then shows of it.
`revealDescendant` stays, for a caller that reveals in one panel directly.

**Who needs to act.** Only a `Panel` subclass that overrides
`revealDescendant` to scroll something other than the panel itself. It
inherits `Panel.revealRect`, which the broker now calls, so its override is
skipped without an error and focus history and spatial navigation no longer
scroll its content into view. Override `revealRect` as well:

```typescript
revealRect(rect: Rect, axis?: ScrollAxis): Rect {
    // Scroll your own inner element the least distance that shows `rect`
    // (browser-viewport coordinates), along `axis` when one is given, and
    // return the part of `rect` that element shows afterwards. Return
    // `rect` unchanged when there is nothing to scroll.
}
```

Override `hasScrollRange(axis?)` too. The inherited one answers for the panel
itself, from its own overflow, and a panel whose own box never scrolls
answers `false`; a list, tree or table inside the subclass would then never
ask it to scroll for a keyboard move. Return whether your inner element can
scroll along `axis`, or `true` when that is not known without measuring.

A subclass whose content scrolls inside an element of its own also overrides
`getScrollViewportElement()` to return that element: spatial navigation reads
it to search the controls of one scrolling area before the rest.

`ScrollStrip` is the library's own case; its `revealRect`, `hasScrollRange`
and `getScrollViewportElement` are the model. A revealer that is not a
`Panel` and implements only `revealDescendant` needs no change: it is still
called, before every scrolling panel.

## `FocusReveal.reveal` scrolls after it returns

**What changed and why.** `FocusReveal.reveal` scrolled every panel around
the control inside the call, outermost first, so a control inside nested
panels, or inside a pane or section that was still opening, could end out
of view. It still selects the tab and expands the pane, region or section
inside the call, so the control can take focus on the next line, but the
scroll now waits until no layout pass is queued around the control and no
`Accordion`, `Split` or `Border` around it is still moving, and then moves
each panel from the innermost out. A reveal into a collapsed `Split` pane
or `Border` region therefore scrolls when the expand ends, about 200 ms
later; under `prefers-reduced-motion: reduce` there is no delay. A waiting
scroll is dropped when the user has moved on: a newer reveal, focus moved
off the control, a modal layer opened over it, or the user scrolled a panel
the scroll would move. The wait ends after 60 layout flushes, one a frame,
so about a second on a 60 Hz display, and the scroll then runs with the
geometry it finds.

**Who needs to act.** Code that measures the control, or a panel's scroll
position, on the line after `FocusReveal.reveal`. Measure it in
`FocusReveal.afterReveal(callback)`, which runs once the scroll of the
latest reveal is over, whether it ran or was dropped, and at once when no
scroll is waiting.

```typescript
// Before
FocusReveal.reveal(handle);
const rect = DOM.source.getElementRect(handle);   // after the scroll

// After
FocusReveal.reveal(handle);
FocusReveal.afterReveal(() => {
    const rect = DOM.source.getElementRect(handle);
});
```

## `FocusHistory`'s `"change"` fires when a flag changes

**What changed and why.** `"change"` fired after every recorded focus move,
every `back()` and `forward()` that moved focus, and every `clear()`,
whether or not
`canGoBack` or `canGoForward` changed. The two flags now say what `back()`
and `forward()` would do from where focus is, and `"change"` fires when
either flag changes value, and only then.

| Moment | Before | Now |
|---|---|---|
| a recorded focus move that leaves both flags as they were | `"change"` | nothing |
| `back()` or `forward()` that leaves both flags as they were | `"change"` | nothing |
| `clear()` with both flags already `false` | `"change"` | nothing |
| focus moves into a table cell's editor, leaving the current stop | nothing | `"change"` when `canGoBack` was `false`; it is now `true` |
| a dialog opens and moves focus into itself | `"change"`, for the dialog's control recorded as a stop | `"change"` when a flag was `true`; both flags are now `false` |
| a modal drawer opens | nothing | `"change"` when a flag was `true`; both flags are now `false` |

**Who needs to act.** A listener that copies the flags onto Back and
Forward buttons needs no change, but should read the flags once when it
subscribes. Code that used `"change"` to learn that a focus move was
recorded has no event for that any more.

```typescript
const sync = (): void => {
    backButton.setEnabled(FocusHistory.canGoBack());
    forwardButton.setEnabled(FocusHistory.canGoForward());
};

FocusHistory.on("change", sync);
sync();   // no event announces the starting state
```

## `DOMSource` gains `readDocumentSelection`

**What changed and why.** `MarkdownEditor` now brings its own selection to
the browser's before it builds a context menu, because on Linux a right-click
moves the browser's caret and raises `contextmenu` before the editor has
followed it. That needs the document's live selection, which Lexical resolves
against the DOM it owns. The read goes through the read seam, like every
other DOM read, so `DOMSource` gains one member:
`readDocumentSelection(reader)`, which hands the live `Selection` (or `null`
when the document has none) to `reader` for the length of the call and
returns what `reader` returns. `getDocumentSelection()` could not carry this:
it reports nothing for a collapsed selection and answers in handles.

**Who needs to act.** Only code that implements `DOMSource` itself — a custom
source installed through `DOM.install`. `ProductionDOMSource` implements it,
and code that only calls the seam is unaffected. A source that wraps another
forwards the call. A source that answers from its own model has no live
selection to hand over and returns `null` without calling `reader`, which
callers treat as "no selection":

```typescript
import type { DOMSource } from '@jimka/typescript-ui/core';

class MySource implements DOMSource {
    // …
    readDocumentSelection<T>(_reader: (selection: Selection | null) => T): T | null {
        return null;
    }
}
```

## `DOMSource` gains `readRangeRects`

**What changed and why.** `MarkdownEditor`'s context menu now opens clear of
the text its items act on, which needs that text's screen rectangles. Lexical
turns a range of its own nodes into a DOM range over the elements it
rendered, and the seam measures it, so `DOMSource` gains one member:
`readRangeRects(build)`, which calls `build` for the range, takes its client
rectangles and returns them as plain `Rect`s. The live `Range` exists only for
the length of the call.

**Who needs to act.** Only code that implements `DOMSource` itself — a custom
source installed through `DOM.install`. `ProductionDOMSource` implements it,
and code that only calls the seam is unaffected. A source that wraps another
forwards the call. A source that answers from its own model has no ranges to
measure and returns `[]` without calling `build`, which callers treat as "no
text to keep clear":

```typescript
import type { DOMSource, Rect } from '@jimka/typescript-ui/core';

class MySource implements DOMSource {
    // …
    readRangeRects(_build: () => Range | null): Rect[] {
        return [];
    }
}
```

## A read-only `MarkdownEditor` or `CodeEditor` refuses its editing commands

**What changed and why.** `setReadOnly(true)` and the `readOnly` option are
documented to reject edits on both surfaces, but only typing was blocked. A
command called from code — `toggleBold()`, `setBlockType()`, `insertTable()`,
the table commands, `cut()`, `paste()` — still changed the document: in
WYSIWYG mode the one on show, so a toolbar wired to those methods edited a
read-only editor, and in `"source"` mode the hidden WYSIWYG document behind
the text. Every command that edits the document is now a no-op while the
editor is read-only, on both surfaces, and `getSelectionState()` reports its
`can…` fields `false`. `paste()` resolves `false` without reading the
clipboard. `copy()`, `setValue()`, `setMode()` and `markClean()` are
unaffected. A read-only `CodeEditor` likewise refuses `cut()`, `paste()` and
`format()` called from code, as it refuses the new `replaceRange()`, and it
now refuses every other change to its document as well, whichever key
binding, handler or language extension makes it: a language you registered
can no longer edit a read-only editor through its own commands.

**Who needs to act.** Only code that used a command, or an extension of a
registered language, to change a read-only editor's document. Load the new text
with `setValue()`, which a read-only editor still accepts, or lift the lock
around the command:

```typescript
editor.setReadOnly(false);
editor.insertTable(2, 3);
editor.setReadOnly(true);
```

A refused command is no longer silent on the WYSIWYG surface either: it
flashes the surface, as the source surface already did for a refused key,
and fires the editor's new `"readonlyedit"` event. Code that calls a command
on a read-only editor and relies on nothing visible happening should test
`getReadOnly()`, or the matching `can…` field of `getSelectionState()`,
first.

A toolbar of your own that enables its Table control on `inTable` stays
enabled over a read-only editor, though its commands are refused: `inTable`
says where a caret or a text selection is (it is `false` while whole table
cells are selected, and for a selection that runs out of its table). Enable
it on `canEditTable || canMergeCells || canUnmergeCell` instead, which are
`false` while the editor is read-only.

## `MarkdownEditorSelectionState` and `CodeEditorSelection` gain required fields

**What changed and why.** `MarkdownEditorSelectionState` gains twelve fields
that say which commands would apply at the selection: `canFormat`,
`canStyle`, `canLink`, `canRemoveLink`, `canSetBlockType`,
`canSetBlockLayout`, `canInsertTable`, `canInsertImage`,
`canInsertHorizontalRule`, `canEditTable`, `canMergeCells` and
`canUnmergeCell`. `CodeEditorSelection` gains `from` and `to`, the
selection's 0-based document offsets. All of them are required.

**Who needs to act.** Only code that builds one of these objects itself — a
test double or a stub event payload, say. The missing fields are a compile
error; add them. Code that only reads the editors' payloads is unaffected.

## `MarkdownEditor.toggleLink(url)` needs a word, a selection or a link

**What changed and why.** `toggleLink(url)` expands a caret to the word
under it. With no word to expand to, it used to link the whole text run the
caret stood in, or the image beside it, which nobody asked for. Outside a
link it now does nothing there, as the command does in `"source"` mode, and
`canLink` is `false`:

| Selection | Before | After |
|---|---|---|
| `hello wo\|rld` | `hello [world](https://z)` | the same |
| `a \| b word`, between two spaces | `[a  b word](https://z)` | nothing |
| `Left column.\|`, after a full stop | `[Left column.](https://z)` | nothing |
| `A [te \| xt](https://x) link.` | the link re-pointed | the same |
| `\|![i](/i.png)`, beside an image | the image linked | nothing |
| the image selected | the image linked | the same |

The menu's Insert link… now follows `canLink`, and the toolbar's Link button
`canLink || canRemoveLink`; before, both also asked for selected text.

**Who needs to act.** Code that called `toggleLink(url)` at a caret and
relied on the whole text run becoming the link: select the text first. A
toolbar of your own enables its Link control on `canLink || canRemoveLink`.

## `MarkdownEditor.paste()` pastes without a text selection

**What changed and why.** With table cells selected, or with no selection,
`paste()` read the clipboard and inserted nothing, though Ctrl/Cmd+V pastes
into selected cells. It now puts the text into the cells, starting at the one
the selection began in, and with no selection at the document's end, where
`insertTable` and `insertImage` insert. The context menu's Paste is always
enabled and now always pastes.

**Who needs to act.** Code that called `paste()` with table cells selected or
with no selection and relied on nothing being inserted.

## `Tree` and `TreeTable` no longer register `caret-down` / `caret-right`

**What changed and why.** `Tree` and `TreeTable` row toggles are now one
`angle-right` glyph, turned 90° to point down when expanded instead of being
swapped for a differently-named glyph — a rotation can be animated with a CSS
transition, and a glyph-name swap cannot. `Tree` and `TreeTable` used to
register `caret-down` and `caret-right` with the shared glyph registry as a
side effect of being imported; they no longer use those names, so that
registration is gone too.

**Who needs to act.** Code that shows a `caret-down` or `caret-right` glyph
elsewhere — a `Button` glyph, an icon renderer's resolver — and relied on
importing `Tree` or `TreeTable` to have registered them for it must now
register them itself:

```typescript
import { Glyph } from '@jimka/typescript-ui/component/display';
import { caret_down, caret_right } from '@jimka/typescript-ui/glyphs/solid';

Glyph.register(caret_down, caret_right);
```

Code that read a tree row's toggle via `getToggle().getGlyphName()` to learn
whether it was expanded should call `Tree.getExpandedNodes()` /
`TreeTable.isExpanded(record)` instead — the glyph name is now `angle-right`
in both states, and the rotation (`getTransform()`) carries the state.

## `Enter` on a `Tree` row fires `"dblclick"`

**What changed and why.** `Enter` on the current row of a focused `Tree`
now does what a double-click on the row does: it fires `"dblclick"`, then
expands or collapses an expandable node. Before, the key did nothing in a
tree, so a node could not be opened from the keyboard. A held key fires
once, and `Enter` with a modifier is left alone. The key is not stopped, so
in a modal `Dialog` with a primary button it confirms the dialog as well.

**Who needs to act.** Code that handles `Enter` itself, in a `keydown`
listener on the tree or an ancestor, to open the current node: remove that
handler, or the node is opened twice. A `"dblclick"` listener that should
run for the mouse alone now also runs for `Enter`.

## `SpatialNavigation`'s region chord is `Ctrl+Alt+Shift`+arrow

**What changed and why.** The `"target"` tier — the chord that jumps
between navigation-target containers — defaulted to `Ctrl+Shift`+arrow.
The service claims its chords at the window before any widget sees them,
so on Windows and Linux it took `Ctrl+Shift+←`/`→` word selection away
from every `<input>`, `<textarea>`, `MarkdownEditor` and `CodeEditor`, and
on macOS it took `CodeEditor`'s `Ctrl-Shift`-arrow bindings. The default is
now `Ctrl+Alt+Shift`+arrow, which no editor or browser binds. The
`"component"` tier stays on `Ctrl+Alt`+arrow.

**Who needs to act.** An app that enables `SpatialNavigation` without
passing `targetModifiers` now answers to `Ctrl+Alt+Shift`+arrow. Update any
help text or shortcut legend that names the old chord. An app that passes
its own `targetModifiers` is not affected. To keep the old chord:

```typescript
SpatialNavigation.configure({ targetModifiers: { ctrl: true, shift: true } });
```

## A `Date` crosses the wire in local form

**What changed and why.** `JsonWriter` and `AjaxProxy`'s `filter=` wrote
every `Date` with `toISOString()`, a UTC instant. That instant no longer
named the calendar day or wall-clock time the user saw: a `date` of 28 June
typed in Tokyo was sent as `2026-06-27T15:00:00.000Z`, and a server that
kept the first ten characters stored the 27th. `JsonWriter` now writes each
top-level `Date` in the form its field type is read back in, and `AjaxProxy`
— whose filter descriptors name a field but not its type — writes every
filter `Date` as local ISO 8601 with its UTC offset.

| Where | Value (local) | Before | After |
|---|---|---|---|
| `JsonWriter`, `date` field | 28 June 2026, 00:00 in Tokyo | `2026-06-27T15:00:00.000Z` | `2026-06-28` |
| `JsonWriter`, `time` field | 09:30:15.250 in Kolkata | `1970-01-01T04:00:15.250Z` | `09:30:15.250` |
| `JsonWriter`, any other field | 28 June 2026, 12:04:59.123 in Los Angeles | `2026-06-28T19:04:59.123Z` | `2026-06-28T12:04:59.123-07:00` |
| `AjaxProxy` `filter=` | 28 June 2026, 00:00 in Tokyo | `2026-06-27T15:00:00.000Z` | `2026-06-28T00:00:00.000+09:00` |

An offset of zero is written `+00:00`, never `Z`. An Invalid `Date` is still
written as `null`, a `Date` nested inside an object or array field value
keeps its `toISOString()` form, and `sort=` is unchanged.

**Who needs to act.** A server that matches a trailing `Z`, or that parses a
`date` value as an instant and relied on the day being UTC's, must parse
each value by its type instead: a bare date, a bare time, or an ISO 8601
date-time with an offset, which any ISO parser reads as the same instant as
before. A consumer who needs the old body can pass a custom `writer` to
`AjaxProxy`.

## A store reads a bare date or a time of day as a local value

**What changed and why.** `Field` converted every `date`, `time` and
`datetime` value with `new Date(raw)`. That read a bare `2026-06-28` as UTC
midnight — 27 June in Los Angeles — and could not read a time of day at all:
`new Date("09:30:00")` is an Invalid Date, so a store `time` column was
always empty. A bare `YYYY-MM-DD` in a `date` or `datetime` field is now
read as local midnight, and a `time` field reads a two-digit
`HH:MM[:SS[.fraction]]` as that time on 1 January 1970, local, to the
millisecond. Any other text still goes through `new Date(raw)`.

| Field type | Raw value | Before | After |
|---|---|---|---|
| `date` | `"2026-06-28"` | UTC midnight | 28 June, 00:00 local |
| `datetime` | `"2026-06-28"` | UTC midnight | 28 June, 00:00 local |
| `time` | `"09:30:15.250000"` | `undefined` | 1 January 1970, 09:30:15.250 local |
| `date` | `"2026-06-28T12:04:00Z"` | that instant | that instant (unchanged) |

0.10.0's migration note says "a store `time` or `datetime` column reads with
`new Date(...)`"; that no longer holds for `time`, nor for a bare-date
`datetime` value. The 0.10.0 page is left as it was released.

**Who needs to act.** Code that relied on a bare date loading as UTC
midnight — for example by reading it back with `getUTCDate()` — should read
it with the local getters. Code that relied on a `time` column being empty,
or that filled it in by hand after load, now receives the stored time.

## `TimeField` values sit on 1 January 1970

**What changed and why.** `TimeField` put a typed or picked time on today's
date. The time cell editor, the filter row and the table's paste path use
1 January 1970, as a store `time` field now does too, so a `TimeField`
bound to a `time` field could mark an untouched value dirty. `TimeField`'s
values now sit on 1 January 1970, local. A relative shorthand is still resolved
against now; only its time of day is kept.

| Input | Before | After |
|---|---|---|
| typed `09:30` on 28 June 2026 | 28 June 2026, 09:30 | 1 January 1970, 09:30 |
| picked 14:45 from the dropdown | today, 14:45 | 1 January 1970, 14:45 |
| typed `+30mi` at 23:50 on 28 June 2026 | 29 June 2026, 00:20 | 1 January 1970, 00:20 |

`setValue` keeps the `Date` it is given, so a value set from code keeps its
own date until the user edits it.

**Who needs to act.** Code that reads the date part of a `TimeField` value,
or compares it with today, should read only its hours, minutes and seconds,
or combine them with the date it wants.

## `Markdown` reads a table only where no other block starts

**What changed and why.** `Markdown` took a line over a delimiter row of
dashes alone as a one-column table, ahead of most other blocks: a setext
heading (`Title` over `---`), a thematic break on the line after a blockquote
or a code fence, a fenced code block whose first line is `---`, and a list
with a bare `-` item all rendered as tables. GFM tries every block that can
start on the header line first, and reads a delimiter row only when a `|` or a
`:` marks it as one; `Markdown` now does the same. Indented or fenced code, an
ATX heading, a thematic break, a blockquote, a list, an HTML block, a link
reference definition and a `:::` fence each win over a table, and a delimiter
row must hold a `|` or a `:`. `MarkdownEditor` loads these documents the same
way.

| Source | Before | After |
|---|---|---|
| `Title` over `---` | a table, header `Title` | a level-2 heading `Title` |
| a code fence, then `---` on the next line | a table with an empty header | a horizontal rule |
| a delimiter row holding a `\|` or a `:` (`a` over `:--`) | a table | a table (unchanged) |

**Who needs to act.** Content that wrote a one-column table with a delimiter
row of dashes alone now renders as a heading. Add a `|` or a `:` to the
delimiter row:

```markdown
<!-- Before: a one-column table -->
Name
---
Ada

<!-- After -->
| Name |
| --- |
| Ada |
```

## A `Dialog`'s first Escape inside an editor releases it

**What changed and why.** A modal `Dialog` whose only focusable content was
a `CodeEditor` trapped a keyboard user: the dialog opened with focus in the
editor, `Tab` and `Shift+Tab` indented and dedented, and `Escape` closed the
whole dialog, so no key reached its buttons. `Escape` inside an editing
surface in a dialog now releases that surface for one `Tab` instead of
closing the dialog, and a second `Escape` closes it. Inside a `Table` the
first `Escape` does not close the dialog either, but the table's own `Tab`
handling can still pull focus back into it.

| Focus | Release armed for this owner? | Key | Result |
|---|---|---|---|
| in the editor | no | `Escape` | release armed; dialog stays open; the editor also receives the Escape |
| in the editor | yes | `Tab` / `Shift+Tab` | focus moves to the dialog's next / previous control, wrapping inside the dialog |
| in the editor | yes | `Escape` | dialog closes with `'close'` |

Any other key, or focus leaving the editor, cancels the release. A mandatory
modal (`dismissable: false`) releases the same way and still ignores the
second `Escape`. To support this, `DismissableLayer.requestClose()` may now
return `false` to decline, and `Dialog.requestClose()` returns `boolean`:
`false` when it armed the release, `true` otherwise.

**Who needs to act.** An automated UI test or script that closes a dialog
with a single `Escape` while focus is in a `CodeEditor`, `MarkdownEditor` or
`Table` must send two, or move focus to a button first. A `Dialog` subclass
that overrides `requestClose(): void` no longer compiles: return `boolean`,
and call `super.requestClose()` and return its result to keep the release.
Other `DismissableLayer` implementations need no change; a `requestClose()`
that returns nothing is handled as before.

## A `Dialog`, a `Window` and a titled `Popover` are named by their title

**What changed and why.** These three layers had no accessible name, so a
screen reader announced none when focus entered them. Each now points
`aria-labelledby` at the component that shows its title: a dialog's title-bar
text, a window's header text, a popover's title row. A browser computes an
element's name from `aria-labelledby` before it looks at `aria-label`, so an
`aria-label` on the same element is ignored while the reference is there.

| Layer | You wrote | Announced before | Announced now |
|---|---|---|---|
| `Window('Local Storage')` | `win.getAria().setLabel('Storage inspector')` | "Storage inspector" | "Local Storage" |
| `new Dialog({ title: 'Delete?' })` | `dialog.getAria().setLabel('Delete record 42')` | "Delete record 42" | "Delete?" |
| `Popover({ title: 'Filters' })` | `popover.getAria().setLabel('Row filters')` | "Row filters" | "Filters" |

A `TabWindow` and a `Drawer` are not affected. A `TabWindow` writes its name
into `aria-label` and leaves a name you set alone; a `Drawer` has no title
and takes whatever name you give it. A `Popover` you name before it gets a
title also keeps your name.

**Who needs to act.** Code that names a `Dialog`, a `Window` or a titled
`Popover` through `getAria().setLabel(…)` after constructing it. Remove the
reference first:

```typescript
win.getAria().clearLabelledBy().setLabel('Storage inspector');
```

For a `Dialog`, `ariaLabel` in the config does the same and also works with
`Dialog.show(config)`, which never hands out the dialog. Code that sets no
ARIA on these layers needs no change.

## The application behind a modal `Dialog` or `Drawer` is inert

**What changed and why.** A modal dialog wrapped `Tab` only while it was the
topmost layer, and only between the first and last element its selector
matched, so focus could leave it: from a context menu or an open `ComboBox`
dropdown on its last control, by `Shift+Tab` after a click on its text, or
past a hidden last control. A modal drawer did not hold focus at all. While a
modal dialog or drawer is open, the library now sets the HTML `inert`
attribute on the rest of the application: every component added to `Body`,
every layer other than the modal and the layers opened from it (the window it
was opened from included), the `Rail`, and each toast's dismiss button. An
inert element cannot be focused, clicked or read by a screen reader. The
library marks its own containers and never `<body>` or `<html>`.

**Who needs to act.**

- Code that relies on the control that opened a modal `Drawer` keeping
  focus: the drawer now moves focus to its first control when it opens, and
  returns it to the opener when it has closed. Handle the keys inside the
  drawer, or listen for its `"close"`.
- Code that calls `element.focus()` on something behind an open modal: the
  call does nothing until the modal closes. Move focus once the modal has
  closed, or put the control inside the modal.
- Code that appends an element by hand to `<body>` or `<html>` and expects a
  modal to block it: the element is not made inert. Build it as a `Popover`
  or `PopupPanel`, or register it as a background surface with
  `LayerManager.addBackgroundSurface`.
- A custom `DismissableLayer` that does not implement `onInertChanged` stays
  focusable and clickable behind a modal. A custom `LayoutManager` that
  mounts a component of its own on its container returns it from
  `getChromeComponents()`, so that it goes inert when the manager is the
  body's.
- An application that supports older browsers: `inert` needs Chrome 102,
  Firefox 112 or Safari 15.5. Without it a modal still opens and `Tab` still
  wraps inside it, but the application behind it can be reached again.

```typescript
import { LayerManager, Panel } from '@jimka/typescript-ui/core';
import type { DismissableLayer } from '@jimka/typescript-ui/core';

class MyLayer extends Panel implements DismissableLayer {
    // …
    onInertChanged(inert: boolean): void {
        this.setInertAttribute(inert);
    }
}

// A component that is not a layer, mounted by hand
LayerManager.addBackgroundSurface({
    onInertChanged(inert) {
        statusBar.setInertAttribute(inert);
    },
});
```

See [Layering: Modal scope](/concepts/layering#modal-scope).

## A `Menu.show()` after a key press takes focus

**What changed and why.** A context menu opened with Shift+F10 or the
ContextMenu key could not be worked from the keyboard: the arrow keys,
`Enter` and `Space` went on acting on the control that had focus.
`Menu.show()` now looks at the last input. After a key press the menu takes
focus, highlights its first enabled row, handles `ArrowDown` / `ArrowUp`,
`Home` / `End`, `Enter` / `Space`, the submenu arrows, `Tab` and `Escape`,
and returns focus to where it was when it closes. After a pointer press it
behaves as before, and so do `toggleFor()` and the `MenuBar` dropdowns.

**Who needs to act.** Code that opens a dropdown with `show()` from its
trigger's own key handler, and expects the trigger to keep focus, opens it
with `toggleFor()` and forwards the trigger's keydowns to the menu:

```typescript
// Before
menu.show(rect.left, rect.bottom, items);

// After
menu.toggleFor(triggerElement, rect, items);

// … and in the trigger's keydown handler
const handled = menu.handleKey(event);
```

A custom `CellEditor` that overrides `retainsFocus` keeps the base answer, so
that its edit stays open while a keyboard-opened context menu holds focus:

```typescript
retainsFocus(relatedTarget: Handle | null): boolean {
    const menuHoldsFocus = super.retainsFocus(relatedTarget);

    // `this.picker` stands for the editor's own dropdown.
    return menuHoldsFocus || LayerManager.containsAcrossLayers(this.picker, relatedTarget);
}
```

## `Markdown` and `MarkdownEditor` read through `marked` 18.1.0

**What changed and why.** The library reads Markdown through `marked`
18.1.0 and pins that exact version. Until now it declared `^18.0.5` and
was tested on 18.0.9. `marked` released 29 changes to its parser in
between, and each one that changes a reading brings it in line with the
CommonMark specification or with GFM. The editor now reads through the
viewer's parser (see Changed), so a document reads the same in both, and
the *Before* column below is the 0.10.0 viewer's reading. A document that
is loaded and saved without an edit is saved byte for byte.

| Source | Before | After |
|---|---|---|
| `[[a](/in)](/out)` — a link written around a link | the link `a` to `/in`; `/out` not shown | the text `[`, the link `a` to `/in`, the text `](/out)` |
| `&#35;`, `&#x23;` — a numeric character reference | shown as typed | the character it names, `#` |
| a line after a fence closed inside a nested quote | not shown at all | a paragraph after the quote |
| `- a`, then `<div` on the next line | the text `<div` in the list item's paragraph | the HTML block after the list |
| a tab in a list item's text | spaces | the tab |
| `[ẞ]` with the definition `[SS]: /url` | literal text | a link: labels match by Unicode case folding, and ignore spaces at their edges |
| `mailto:a@b.cc`, `xmpp:a@b.cc/x` as bare text | a link on the address alone | a link on the whole, as GFM specifies |
| `Foo`, an indented line, then `===` | a paragraph | a heading |
| `foo`, then a code fence alone on the last line | one paragraph holding the fence | the paragraph `foo`, then an empty code block |
| `*a*\🙂` — emphasis, then a backslash and an emoji | emphasis holding `a*`, then `🙂` | emphasis holding `a`, then `\🙂` |

In the editor, text typed as `&#35;` is now saved as `\&#35;`, so that it
stays the text that was typed.

**Who needs to act.** Nothing fails to compile. Review content that relies
on one of the readings in the *Before* column. The one most likely to
matter is a link written around a link: write the outer text without a
link inside it, or keep only the inner link.

```markdown
<!-- Before: showed "docs" linked to /in -->
[[docs](/in)](/out)

<!-- After: pick one target -->
[docs](/in)
```

An application that showed `&#35;` or `&#169;` as literal text on purpose
writes `\&#35;` instead.

## `Markdown` and `MarkdownEditor` read named character references

**What changed and why.** A character reference is `&`, a name or a
number, and `;`. CommonMark reads every reference whose name is in the
HTML list as the character it names, in text, a link's destination and
title, and a code fence's info string. In 0.10.0 the viewer read neither
kind, and the editor read only a decimal numeric reference (`&#35;`), in
text and in a link's destination and title; `marked` 18.1.0 reads numeric
references in text (see the note above). The library now reads both kinds
wherever CommonMark does, in the viewer and the editor alike.

| Source | Before | After |
|---|---|---|
| `&copy; &amp; &nbsp;` | shown as typed | `©`, `&`, a no-break space |
| `[a](/f&ouml; "&#x23;1")` | links to `/f&ouml;`, titled `&#x23;1` | links to `/fö`, titled `#1` |
| ```` ```j&#115; ```` | a code block of language `j&#115;` | of language `js` |
| `# Terms &amp; Conditions` | `id="terms-amp-conditions"` | `id="terms-conditions"` |
| `&notaname;`, `&copy` (no `;`), a reference in code, an autolink, an HTML block, a tag's attributes, or between `<code>`, `<pre>`, `<kbd>` or `<script>` and its end tag | shown as typed | shown as typed (unchanged) |

In the editor, text typed as `&copy;` is now saved as `\&copy;`, so that it
stays the text that was typed.

**Who needs to act.** Nothing fails to compile. Content that shows a
named reference as literal text on purpose escapes its `&`:

```markdown
<!-- Before: showed "&copy;" -->
&copy;

<!-- After -->
\&copy;
```

A `#fragment` link to a heading whose text holds a reference changes to the
new id.

## `MarkdownEditor.setBlockType("quote")` toggles

**What changed and why.** A quote now holds blocks, as Markdown's does, so
the quote is no longer a block type among the others: it is a container
the blocks stand in.

| Call | Before | Now |
|---|---|---|
| `setBlockType("quote")` on two paragraphs | two quotes | one quote holding both |
| `setBlockType("quote")` in a quote | nothing | the blocks leave the quote |
| `setBlockType("paragraph")` in a quote | the quote becomes a paragraph | the paragraph stays in the quote |
| `setBlockType("h2")` in a quote | the quote becomes a heading | a heading in the quote |
| `toggleUnorderedList()` in a quote | the quote becomes a list item | a list in the quote |
| `insertTable()` in a quote | the quote split at the caret around the table, leaving an empty quote above it or below it when the caret was at the quote's start or end | the table in the quote |

A block typing shortcut typed at the start of the paragraph of a quote of one
paragraph now builds inside the quote, as it does in a quote of several blocks.
Lexical's own shortcuts replaced such a quote before:

| Typed at the start of `b` in `> b` | Before | Now |
|---|---|---|
| `- ` | `- b` | `> - b` |
| `# ` | `# b` | `> # b` |
| a code fence and a space | a code block outside the quote | a code block inside the quote |
| `> ` | `> b` | `> > b` |

`setBlockType("quote")` over a raw Markdown block puts it into a quote and keeps
it raw (`> <div>x</div>`).

**Who needs to act.** Code that removes a quote with
`setBlockType("paragraph")` calls `setBlockType("quote")` instead. A toolbar
that wires its Quote button to `setBlockType("quote")` needs no change: the
button now toggles.

## Thematic breaks (`---`) are horizontal rules in `Markdown` and `MarkdownEditor`

**What changed and why.** A thematic break (`---`, `***` or `___`, with the
spaces, tabs and up to three spaces of indentation CommonMark allows) is now a
construct of its own on both surfaces. `Markdown` rendered it through its
plain-text fallback, so the literal `---` showed (a `---` on the line after
a code fence or a blockquote read as a table, as the note on tables says);
`MarkdownEditor` loaded it as a paragraph of text. The viewer renders an
`<hr>`, and the editor has a node for a rule, saved as it was written (a
rule typed in the editor is saved as typed, and one from
`insertHorizontalRule()` as `---`).

| | Before | Now |
|---|---|---|
| `---` in `Markdown` | the literal text `---` | an `<hr>` |
| `---` in `MarkdownEditor` | a paragraph holding the text `---` | a horizontal rule node, saved as written |

**Who needs to act.** Content that used `---` as visible text writes `\---`
(or puts it in a code span). Code that read the editor's tree for a
paragraph holding `---` reads the `markdown-horizontal-rule` node instead.

```markdown
<!-- Before: showed the text --- -->
---

<!-- After: still shows the text -->
\---
```

## Task-list items show a checkbox in `Markdown` and `MarkdownEditor`

**What changed and why.** A GFM task-list item (`- [ ] todo`, `- [x] done`,
also under `*`, `+` and ordered markers, nested, in loose and tight lists) had
no checkbox. The viewer dropped the marker of a plain item in a tight list and
showed only its text; it showed the marker as text where the item's text held
an escape or formatting and in a loose list, on a line of its own when a blank
line inside the item made it loose. The editor showed the marker as ordinary
text. The viewer now draws a read-only checkbox in its place, and the editor
holds a checkbox node of its own that a click or Ctrl/Cmd+Enter toggles.

| | Before | Now |
|---|---|---|
| `- [ ] a` in `Markdown` | `a` alone in a tight list (`[ ] a` when the text is formatted or the list is loose) | a read-only checkbox (`role="checkbox"`, `aria-checked`), then `a` |
| `- [ ] a` in `MarkdownEditor` | the text `[ ] a` | a checkbox node of type `markdown-task-checkbox` |
| bold over `- [ ] a` from before the marker | `- **[ ] a**`, no longer a task item | formats the text: `- [ ] **a**` |
| `toggleTaskList()` | not there | makes or removes task items |

**Who needs to act.** CSS or tests that read the viewer's `[ ] ` text read the
`role="checkbox"` span instead. Code that read the item's text for a leading
`[ ] ` reads the checkbox node. Content that showed `[ ]` as text at an item's
start on purpose writes `\[ \]`.

```markdown
<!-- Before: showed the text [ ] a -->
- [ ] a

<!-- After: shows a checkbox; to keep the text, escape it -->
- \[ \] a
```

## `Markdown` and `MarkdownEditor` read every CommonMark image form

**What changed and why.** The viewer read an image only as `![alt](src)`,
with no brackets in the alt text and no space or parenthesis in the source.
Every other CommonMark image form showed its alt text as plain text. The
viewer and the editor now read an image with a title, a reference image
(`![alt][label]`, `![label][]`, `![label]`), an angle-bracket destination and
images or links in the alt text as CommonMark does, and the `{width=…
height=…}` group works after every form. A title becomes the `<img>`'s
`title` attribute, and the alt text is the description's plain text.

| Source | Before | Now |
|---|---|---|
| `![a](/u "t")` | the text `a` | `<img src="/u" alt="a" title="t">` |
| `![a][r]` with `[r]: /i.png` | the text `a` | `<img src="/i.png" alt="a">` |
| `![a](<b.png>)` | `<img src="<b.png>">` | `<img src="b.png">` |
| `![a *b*](u.png)` | `alt="a *b*"` | `alt="a b"` |
| `![a](/a\_b.png)` | `<img src="/a\_b.png">` | `<img src="/a_b.png">` |
| `MarkdownEditor.insertImage(src, { alt: 'a[b]' })` | inserts the image, saved as `![a[b]](src)`, which reloads as text | inserts the image, saved as `![a\[b\]](src)` |

**Who needs to act.** Content that relied on a titled or reference image
showing its alt text as text writes that text instead, or escapes both
brackets to show the source as typed (`!\[a\]\[r\]` shows `![a][r]`); an
escaped `!` alone (`\![a][r]`) shows a `!` followed by a link, not text.
An image's destination and title now read backslash escapes and character
references, as a link's do: `![a](/a\_b.png)` had the `src` `/a\_b.png` and
now has `/a_b.png`, so an address that held a literal backslash writes it
doubled. Code that read the editor's tree for a titled or reference image as
text reads the `markdown-image` node and its `getTitle()`. Tests that
asserted an `<img>`'s `alt` or `src` for alt text with escapes or a `<…>`
destination expect the read values.

```markdown
<!-- Before: showed the text "logo"; after: shows the image -->
![logo][l]

[l]: /img/logo.png

<!-- To keep the source as text: escape both brackets, which shows ![logo][l] -->
!\[logo\]\[l\]

<!-- To keep the old output, write the alt text itself -->
logo
```

## Table-cell line breaks are saved as `<br>`

**What changed and why.** `MarkdownEditor` 0.10.0 saved a line break in a
table cell, Shift+Enter's, as a single `\n` inside the cell (`| x\nz |`).
Its own loader read that back as a line break, but the `Markdown` viewer
showed the two characters `\n`, so the same document read differently in
the two. The editor now saves the break as `<br>`, which both read as a
line break, and it loads a `\n` in a cell as the viewer shows it: as text.

| Cell source | 0.10.0 editor | 0.10.0 viewer | Now, in both |
|---|---|---|---|
| `x\nz` | `x`, a line break, `z` | the text `x\nz` | the text `x\nz` |
| `x<br>z` | the text `x<br>z` | the text `x<br>z` | `x`, a line break, `z` |

**Who needs to act.** Documents that the 0.10.0 editor saved with a line
break in a table cell. Replace each such `\n` with `<br>` to keep the
break; the editor and the viewer then both show it. A cell that has been
edited since is saved with the backslash escaped, `\\n`; replace that the
same way.

```markdown
<!-- Before: a line break in the 0.10.0 editor, the text \n in the viewer -->
| Name | Address |
| --- | --- |
| Ada | 12 Hill Road\nLondon |

<!-- After: a line break in both -->
| Name | Address |
| --- | --- |
| Ada | 12 Hill Road<br>London |
```
