This is a read-only audit: it catalogues state that a future release-and-rebuild
feature would lose or dangle, and prescribes no code change. Verdicts on
Table A rows are advisory for the follow-up plan that designs the release API.

## Verified assumptions

- **Lazy re-materialization.** `Component.getElement(createIfMissing)` returns
  the cached `_element` handle if set. Otherwise it first tries
  `DOM.source.getElementById(this.getId())`, and only when *that* lookup
  misses does it fall back to `render()` (when `createIfMissing` is true)
  [Component.ts:863-876](packages/lib/src/typescript/lib/core/Component.ts#L863-L876).
  This id-lookup step is the whole risk surface for the feature this
  catalogue serves: a release that clears `_element` without also removing
  the node from the document resurrects the *dead* element by id and never
  calls `render()` at all — the "lazy re-materialization" the feature
  depends on only happens if release also detaches the node.
- **Id-keyed event routing.** `Event` installs exactly one window-level
  capture listener per event type ([Event.ts:101](packages/lib/src/typescript/lib/core/Event.ts#L101)) and dispatches by
  interning the browser target into a `Handle`, resolving `DOM.source.getId(handle)`,
  and walking up the handle chain matching against id-keyed listener maps —
  never against a live element reference
  ([Event.ts:139-186](packages/lib/src/typescript/lib/core/Event.ts#L139-L186)). A listener registered through `Event`
  therefore survives a rebuild automatically, as long as the fresh element
  carries the same id (which `init()` sets unconditionally — see below). This
  is true for *dispatch* — but not the whole story: an `init()` override that
  calls `Event.addListener`/`addSubtreeListener` unconditionally re-registers
  on every rebuild, and nothing dedupes the result. See "A third failure
  shape" below, which this catalogue's two-table format cannot represent on
  its own.
- **What `init()` already replays onto a fresh element**
  ([Component.ts:5245-5297](packages/lib/src/typescript/lib/core/Component.ts#L5245-L5297)): the id (`DOM.sink.setId`), the class
  name (`addClass`), the buffered inline style (`_inlineStyle.attach`, replaying
  every queued `setElementStyle`/`setElementCSSRule` write), the `_attributes`
  map, `_disabledAttribute`, `_options.attributes`, ARIA (`_aria.applyToElement`),
  `applyStyle(element)`, and re-appending each existing child component's
  element (via `this.getComponents()`, i.e. `_components` — **not** any raw
  child element a subclass manages directly). Anything on this list is
  `accept-loss` by default (already handled) — the interesting rows are what
  is *not* on it, or what is written on top of it by a subclass's own
  `init()`/`render()` override.
- Two claims from the plan's scoping needed no re-derivation, confirmed
  unchanged: no `ResizeObserver`/`IntersectionObserver`/`MutationObserver`
  appears anywhere in the library, and there is no `<details>`, `<dialog>`,
  or native `checked` state (`Checkbox` keeps selected/indeterminate in
  `_options` and draws its own mark).

## A third failure shape — id-routed listeners double-register on rebuild

Neither Table A nor Table B fits this: it is not state a rebuild loses (Table
A), and it is not a JS field left pointing at a dead element (Table B). It is
a *third* shape the plan's two tables did not anticipate — a side effect that
fires **twice** after a rebuild instead of the DOM-only state being lost or
stale. The "Id-keyed event routing" verified assumption above is only half
the story: it is true that a listener registered through `Event` keeps
matching the fresh element by id, but nothing stops the *same* `init()`
override from calling `Event.addListener`/`addSubtreeListener` again on every
rebuild. `Event.addListener` ends its registration path with an unconditional
`compFunc.listeners.push(listener)` ([Event.ts:299](packages/lib/src/typescript/lib/core/Event.ts#L299)), and `addSubtreeListener`
does the identical thing ([Event.ts:391](packages/lib/src/typescript/lib/core/Event.ts#L391)) — neither checks whether the exact
listener reference is already present for that component id before pushing.

**This shape is not bounded by the seam grep.** The rest of this catalogue's
completeness rests on the two greps in the Coverage section, because DOM-only
*state* cannot exist outside the `DOM` seam. This failure shape is different:
it depends on `Event` registration, not `DOM` access, so a class can exhibit
it while never once calling `DOM.sink`/`DOM.source` directly — `ParentHeader.ts`
and `ResizeHandle.ts` below are both outside the 104-file seam grep for
exactly that reason. What *would* bound this shape is a third grep —
`grep -rl 'Event\.add\(Listener\|SubtreeListener\|ViewportListener\)('
src/typescript/lib` — intersected with the files returned by
`grep -rln 'protected init(' src/typescript/lib`, with each intersection
manually checked for whether the registration inside `init()` is
unconditional (most are guarded, constructor-time, or registered from a
method other than `init()`). That intersection was run for this correction
pass; it is cheap (16 candidate files) and every one was checked, so the
table below is now the complete set, not a sample:

(so a release+rebuild double-registers every listener below, and each fires
twice per dispatched event thereafter):

**One exclusion.** `core/Body.ts` (the viewport-sized, `document.body`-backed
singleton, not `component/table/Body.ts` above) also registers
`Event.addViewportListener(this, "resize", this._onViewportResize)`
unconditionally from `init()` ([core/Body.ts:85](packages/lib/src/typescript/lib/core/Body.ts#L85)),
ending in the same undeduped push. It is excluded from the table above
because `core/Body.ts` overrides `getElement()` to always return
`DOM.source.getBody()` ([core/Body.ts:70-72](packages/lib/src/typescript/lib/core/Body.ts#L70-L72))
— it can never go through `render()` again, so it can never rebuild and this
shape can never fire for it. (A second candidate reviewed and *not* included:
`AbstractSelectableList.ts:508`'s `init()` does not call `Event.addListener`
at all — the listeners at `AbstractSelectableList.ts:317-320` are wired at
construction time, not from `init()`.)

This repo has a recorded prior incident of exactly this class (see the
`feedback_rewiring_stacks_listeners` project note: re-running listener
registration on a surviving component stacks duplicate listeners). The
follow-up feature plan that consumes this catalogue must handle this shape
explicitly — either by having the release/rebuild path call
`Event.removeListener`/`removeSubtreeListener` for every listener an `init()`
override is about to re-register (which the `HeaderCell` closures above make
impossible without a code change to hold stable references), or by making
registration idempotent in `Event` itself. Neither option is this audit's to
choose; it is a code change, and this is a read-only inventory.

probe: `packages/lib/tests/component/dom-state-replay-probe.test.ts` proves
the mechanism directly — a `Component` subclass whose `init()` registers one
listener unconditionally needs *two* `Event.removeListener` calls to fully
unregister after a single rebuild, where a correctly-deduped registration
would need only one.
