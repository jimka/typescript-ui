# Style Audit CI Regression Ratchet — Implementation Plan

## Overview

The Style Audit diagnostic ([`packages/lib/src/typescript/lib/diagnostics/StyleAudit.ts`](packages/lib/src/typescript/lib/diagnostics/StyleAudit.ts)) scans the shared stylesheet for `#id`-scoped rules whose declaration body duplicates another instance's — the symptom of CSS that should live at the class or state tier but is instead written per instance. Today the only automated coverage is [`packages/lib/tests/diagnostics/StyleAudit.test.ts`](packages/lib/tests/diagnostics/StyleAudit.test.ts), which exercises the scan's own mechanism (grouping, sorting, the 25-row cap) against synthetic `StyleRule` fixtures it builds itself. It says nothing about whether the real framework's rendered components currently duplicate any CSS, and nothing stops a future change from reintroducing the duplication pattern that several prior plans manually found and fixed by opening a browser and running the live audit.

This plan adds a second, independent test — [`packages/lib/tests/diagnostics/StyleAudit.regression.test.ts`](packages/lib/tests/diagnostics/StyleAudit.regression.test.ts) — that builds and mounts a broad, real gallery of framework components (not synthetic fixtures), runs `auditStyleRules()` against the resulting live stylesheet, and asserts the duplicate count does not exceed a checked-in ceiling constant. It also adds a CI workflow that actually runs this test on every push and pull request, because the repository currently has none for `packages/lib`.[^no-ci-today]

## Architecture Decisions

### The gallery is a new, dedicated fixture — not the docs app or the library's own dev app

The library ships two things that already render "many real components together": the docs site's demo catalogue (`packages/docs/src/demos/*.ts`, resolved by [`packages/docs/src/content/demos.ts`](packages/docs/src/content/demos.ts)) and the library's own dev-server app (`packages/lib/src/typescript/main.ts` and its ~30 `*Panel.ts` siblings, e.g. [`packages/lib/src/typescript/ComplexUIPanel.ts`](packages/lib/src/typescript/ComplexUIPanel.ts)). Neither is reused here. The gallery is a new set of component instances built directly inside the new test file, using the same `~/...` internal import style [`packages/lib/tests/component/default-options-fallback.test.ts`](packages/lib/tests/component/default-options-fallback.test.ts) already uses.[^why-not-app-reuse]

### Kept in a separate file from `StyleAudit.test.ts`, not folded in

`StyleAudit.test.ts`'s tests assert *exact* counts (e.g. "two rules make one duplicate row with count 2") against the live, process-wide `_ruleCache` that `styleRuleEntries()` reads (see [`packages/lib/src/typescript/lib/core/StyleTarget.ts:188`](packages/lib/src/typescript/lib/core/StyleTarget.ts#L188)). Mounting dozens of real gallery components in the same file would pollute those exact counts. Vitest isolates each test *file*'s module graph by default (no `isolate: false` in [`packages/lib/vitest.config.ts`](packages/lib/vitest.config.ts)), so keeping the gallery in its own file is what keeps the two kinds of test from interfering with each other.[^separate-file-safety]

### The ceiling is a single hand-edited constant, not a generated baseline file

`scripts/eslint/no-raw-dom.baseline.json` and `scripts/eslint/require-content-bounds.baseline.json` are this codebase's existing precedent for a shrink-only, checked-in ratchet: a generated list of specific offending sites, regenerated by `npm run lint:baseline`, that only shrinks as sites are fixed (see ARCHITECTURE.md, *Positioning is always absolute*: "Baseline entries come out as sites are fixed and none should go in"). This plan follows the same spirit — a checked-in ceiling that only the person who legitimately needs to raise it touches — but as one number with a policy comment, not a generated per-site file, because a duplicate "body" (a CSS declaration string) is not a stable per-site identity the way a lint offense's `file:line` is; two different components can incidentally produce the same body across unrelated commits, so a per-row baseline would drift and need regeneration for reasons that have nothing to do with real duplication. A single `STYLE_AUDIT_DUPLICATE_CEILING` constant, defined once in the new test file with a comment stating the bump policy, gives the same "a reviewer sees this line change in the diff" property with none of that churn.

### The assertion is a ceiling (`toBeLessThanOrEqual`), not exact equality

The test asserts `duplicates.length <= STYLE_AUDIT_DUPLICATE_CEILING`, not `=== `. An equality check would fail every unrelated PR that happens to reduce the count without also editing the constant in the same PR, which is noisy for a project that biases toward surgical, minimal-diff changes. The tradeoff is that the ceiling can go stale (stay looser than the current real count) until someone notices and tightens it — accepted deliberately, matching the "does not exceed" framing of the goal.[^ratchet-vs-equality]

### Table row-body virtualization is not exercised; Cell coverage comes from standalone instances instead

A throwaway probe run in this plan's worktree (not shipped) confirmed that mounting a real `Table` with a `MemoryStore`, giving it an explicit pixel width/height, and calling `flushLayout()` renders the table's header row (`HeaderCell`, `HeaderCellRenderer`, `HeaderCellText`, `TableHeaderMenuButton`) correctly under plain `jsdom` — but renders **zero** body rows (no `Row`/`Cell` descendants under `TableBody` at all). The same setup applied to a `List({ items: [...] })` *did* fully populate its row pool (three real `SelectableListRow` instances) and did produce genuine duplicate rows in `auditStyleRules()`'s output. Table's body virtualizer is therefore the one thing in this gallery that doesn't render under `jsdom`; body-`Cell` coverage comes instead from two standalone `StringCell` instances, built directly (zero-argument constructor, the same pattern `default-options-fallback.test.ts` already uses), bypassing the Table body virtualizer entirely. Body-level `Row` duplication is out of scope — see `## Non-Goals`.[^probe-evidence]

### CI does not run `packages/lib`'s test suite today; this plan adds a minimal workflow for it

The only workflow in `.github/workflows/` is `docs.yml`, and it (a) triggers only on `push` to `master` plus `workflow_dispatch` — never on a pull request — and (b) only runs `packages/docs`'s typecheck and test, never `packages/lib`'s. So today, nothing gates `packages/lib`'s ~5,000 existing tests — including the mechanism test this plan's ratchet sits beside — before a PR merges. Calling the new test "CI-enforced" would not be true without fixing this, so this plan adds one small workflow file that runs `npm run test` (root script, delegates to `packages/lib`) on `pull_request` (the pre-merge gate) and on `push` to `master` (mirroring `docs.yml`'s own trigger). It does not touch `docs.yml`, and it does not attempt to close any other CI gap (lint, `packages/create-app`, docs test triggers) — those are pre-existing, unrelated gaps.[^no-ci-today]

## Internal Structure

`StyleAudit.regression.test.ts`'s shape:

```typescript
// @vitest-environment jsdom
import { describe, it, expect } from 'vitest';
import { Component } from '~/core/Component';
import { Panel } from '~/core/Panel';
import { VBox } from '~/layout/VBox';
import { LayerManager } from '~/core/LayerManager';
import { auditStyleRules } from '~/diagnostics/StyleAudit';
import { MemoryStore } from '~/data/MemoryStore';
import { Model } from '~/data/Model';
import { Table } from '~/component/table/Table';
import { List } from '~/component/list/List';
import { StringCell } from '~/component/table/cell/String';
// ...one import per gallery class, matching default-options-fallback.test.ts's imports.

const NOOP = (): void => {};

// Ratchet ceiling for the live-gallery duplicate count (see `## Architecture
// Decisions` -> "The ceiling is a single hand-edited constant"). Lower this
// number in the same PR that fixes a dedup root cause. Raise it ONLY with a
// comment here explaining why (e.g. a new component structurally can't yet
// share class-tier CSS) — never raise it just to make a failing test pass
// without first reading the audit's own duplicate rows for a fixable cause.
const STYLE_AUDIT_DUPLICATE_CEILING = /* set from the real run — see Step 4 */;

// One factory per gallery class. Each constructor call is copied verbatim
// from an existing, already-passing call in default-options-fallback.test.ts.
const GALLERY_FACTORIES: Array<() => Component> = [
    () => new TextField(),
    () => new Button('x'),
    // ... full list in `## Ordered Implementation Steps`, Step 2.
];

function buildGallery(): Component {
    const root = new Panel({ layoutManager: new VBox() });
    root.setWidth(1200);
    root.setHeight(6000);

    for (const build of GALLERY_FACTORIES) {
        root.addComponent(build());
        root.addComponent(build());
    }

    // Table: header-only coverage (see the probe-evidence footnote).
    const model = new Model([{ name: 'a', type: 'string' }, { name: 'b', type: 'string' }]);
    const store = new MemoryStore({ model, data: [{ a: '1', b: '2' }], autoLoad: true });
    root.addComponent(Table(store));

    // List: real row-pool duplication coverage.
    const list = List({ items: ['a', 'b', 'c'] });
    list.setWidth(400);
    list.setHeight(200);
    root.addComponent(list);

    // Standalone body-Cell coverage (Table's own body virtualizer doesn't
    // render under jsdom — see the probe-evidence footnote).
    root.addComponent(new StringCell());
    root.addComponent(new StringCell());

    return root;
}

describe('auditStyleRules — live gallery regression ratchet', () => {
    it('the live gallery has no more duplicate style rules than the checked-in ceiling', () => {
        const root = buildGallery();

        LayerManager.mount(root.getElement(true)!);
        root.flushLayout();

        const { duplicates } = auditStyleRules();

        expect(duplicates.length).toBeLessThanOrEqual(STYLE_AUDIT_DUPLICATE_CEILING);

        root.dispose();
    });
});
```

## Expected Behaviour

- Building the gallery (Step 2-3) produces at least 45 distinct component classes with two real instances each, plus the Table's header row, three real `List` rows, and two standalone `StringCell` instances, all constructed without throwing.
- Mounting the gallery root via `LayerManager.mount(root.getElement(true)!)` and calling `root.flushLayout()` renders the full subtree — every gallery component's `getElement()` returns a real, attached DOM node.
- `auditStyleRules()` run immediately after returns a `duplicates` array whose `.length` is `<= STYLE_AUDIT_DUPLICATE_CEILING`. This is the one behaviour this plan pins with an assertion; everything else in this list is a precondition for that assertion to be meaningful, not a separate thing to test.
- If a future change reintroduces per-instance CSS that should be class-tier-shared for any of the classes in this gallery, `duplicates.length` grows past `STYLE_AUDIT_DUPLICATE_CEILING` and the test fails — this is the regression this plan exists to catch. Not independently testable without actually introducing such a regression; covered instead by the ceiling assertion above plus manual confirmation during Step 4 that the test *can* observe a nonzero count (the List rows already proved this in the worktree probe).
- `root.dispose()` at the end of the test does not itself need an assertion — it exists so the test doesn't leave rules behind for any other test that happens to run in the same worker process, matching the pattern (dispose after assert, no `try`/`finally`) `StyleAudit.test.ts` already uses.
- Manual verification: none required — everything above is exercised by the single automated test.

## Potential Challenges

- **Some gallery class throws or hangs under `jsdom`.** Mitigation: the try-and-drop allowance in Step 2 — remove the one offending factory with a comment, don't chase the root cause here.
- **The observed baseline is unstable because other dedup plans land around the same time.** Mitigation: Step 4 always re-derives the number from this worktree's own `master` at implementation time, never from a number written into this plan.
- **A future contributor raises `STYLE_AUDIT_DUPLICATE_CEILING` reflexively to unblock a failing PR.** Mitigation: the comment directly above the constant states the policy (read the audit's own duplicate rows for a fixable cause before raising it); this is a documentation control, not a mechanical one — consistent with how the existing ESLint baseline convention documents its own shrink-only intent in prose rather than enforcing it in code.
- **The gallery grows stale as new component classes are added to the library without ever being added here.** Out of scope for this plan — see `## Non-Goals`.

## Non-Goals

- **Table/Tree body-row (`Row`-level) duplication is not reproduced.** Only `Cell`-level coverage is added, via standalone `StringCell` instances. Making Table's body virtualizer render under `jsdom` (or extending the modelled DOM harness to also fake real `cssText`) is a separate, larger undertaking with its own design tradeoffs — not part of this plan.
- **No change to `StyleAudit.ts` / `StyleAuditView.ts` / `StyleAuditOverlay.ts`.** This plan is test-only.
- **No baseline-regeneration script.** A single hand-edited constant is enough at this scale; see `## Architecture Decisions`.
- **No broader CI buildout.** The new workflow runs only `packages/lib`'s existing `npm run test` script. It does not add lint gating, `packages/create-app` testing, or a `pull_request` trigger for `docs.yml` — those are pre-existing gaps unrelated to this plan's purpose.
- **No attempt to keep the gallery exhaustive.** It is a broad, curated sample (~50 classes, two instances each, plus Table/List/Cell coverage), not an enumeration of every component class in the library. A class added to the library after this plan lands is not automatically covered.
- **The exact baseline number is not fixed by this plan.** Seven other dedup plans may land before or after this one; Step 4 explicitly re-derives the number from whatever `master` looks like at implementation time.

## Notes

[^no-ci-today]: The only workflow file in the repository is `.github/workflows/docs.yml`. It triggers on `push: branches: [master]` plus `workflow_dispatch` — never on a pull request — and its only test-running steps are `npm -w packages/docs run typecheck` and `npm -w packages/docs run test`. `packages/lib`'s own `npm run test` (`typecheck:test` + `vitest run`, confirmed in `packages/lib/package.json`'s `scripts` block) is not invoked by any workflow. There is no Husky pre-push hook running tests either (the only mechanically-enforced local hook found is the commit-message format hook, unrelated to test execution). This means every existing test in `packages/lib` — including this plan's new one — currently runs only when a developer remembers to run it locally.

[^why-not-app-reuse]: Two candidates were investigated and rejected. (1) `packages/docs/src/demos/*.ts` imports the library via the `@jimka/typescript-ui` package name, which `packages/docs/package.json` depends on as `"*"` — a real package resolution, not a source alias — so importing a demo module into a `packages/lib` test would pull in `packages/lib/dist/`, which is gitignored and only rebuilt by an explicit `npm run build:lib` step; a test whose correctness silently depends on a possibly-stale build defeats the point of a regression gate. (2) `packages/lib/src/typescript/*.ts` (the library's own dev-server app, e.g. `ComplexUIPanel.ts`, `main.ts`) imports via the *same* `@jimka/typescript-ui/*` specifier, but `packages/lib/vite.config.ts:6-30` aliases that specifier back to `src/typescript/lib/*` — so, unlike the docs app, it actually does resolve to current source when built or tested from within `packages/lib`. It was still rejected: `packages/lib/tsconfig.test.json`'s `include` is `["tests/**/*", "src/typescript/lib/**/*"]` — the app's `*Panel.ts` files sit outside that set, a type-checking boundary no existing test currently crosses; reusing demo content would also couple the ratchet's baseline to unrelated demo-copy edits (someone tweaking `BindingPanel`'s sample text could shift the count for a reason that has nothing to do with CSS); and the app's heaviest file, `MiscPanel.ts` (2,195 lines: `WebGLCanvas`/`Canvas` animation loops, a 400-row synthetic table), is unsafe and slow under `jsdom` and would need to be hand-excluded regardless — so "just reuse the app" isn't actually a clean drop-in, and a dedicated gallery ends up no more work while avoiding both risks.

[^separate-file-safety]: Vitest's default test isolation runs each test *file* in its own module graph (no `isolate: false` override found in `packages/lib/vitest.config.ts`), so a module-level cache like `StyleTarget.ts`'s `_ruleCache` starts fresh per file. `StyleAudit.test.ts`'s own header comment already documents this dependency for its own tests ("`_ruleCache` ... stays clean for the next one"). As long as the gallery stays in its own file, this isolation is what keeps its ~100 real component instances from corrupting `StyleAudit.test.ts`'s exact-count assertions, and vice versa.

[^probe-evidence]: A throwaway test file was written and run in this plan's worktree (not committed, removed before finishing) to check jsdom's behavior empirically rather than guess. First: a `Table` built from a `MemoryStore`, given an explicit `setWidth(800)`/`setHeight(400)`, mounted via `LayerManager.mount`, with `flushLayout()` called — the header rendered correctly (`HeaderCell`, `HeaderCellRenderer`, `HeaderCellText`, `TableHeaderMenuButton` all present in the subtree, `table.getWidth()`/`getHeight()` resolved to real numbers), but zero `Row`/`Cell` descendants appeared under `TableBody` — the body virtualizer produced no rows at all, evidently gated on some real-DOM measurement (most likely font metrics or scroll-container geometry) that `jsdom` reports as zero. Second, identical harness: `List({ items: ['a', 'b', 'c'] })`, given an explicit `setWidth(400)`/`setHeight(200)`, fully populated its row pool (three real `SelectableListRow` instances materialized), and `auditStyleRules()` reported `componentRuleCount: 5` against `uniqueBodyCount: 3` — genuine, correctly-detected duplication. This is the evidence behind treating Table as header-only coverage and reaching for standalone `StringCell` instances (already proven constructible with a zero-argument constructor by `default-options-fallback.test.ts`) for `Cell`-level coverage instead.

[^ratchet-vs-equality]: An exact-equality assertion (`toBe(ceiling)`) was considered, since it would force the ceiling to tighten the moment any fix landed rather than allowing it to go stale. It was rejected because it fails every unrelated PR that happens to reduce the duplicate count without also remembering to edit the constant in the same PR — noisy for a project whose stated bias (`CLAUDE.md`, *Surgical Changes*) is toward minimal, focused diffs. The chosen ceiling check accepts that the number can go stale in the loose direction until a human notices and tightens it, same as the existing ESLint baseline files (which are also not automatically re-tightened on every green run — they require someone to run `npm run lint:baseline` deliberately).

## Implementation Notes

- **`NumberSpinner` dropped from the gallery** (Step 2's try-and-drop allowance). Its layout pass calls `getBaseline()` -> `Util.measureTextBaseline()`, which needs a canvas 2D context (`ctx.font = ...`); jsdom does not implement `HTMLCanvasElement.getContext()` without the optional `canvas` npm package, so the whole gallery's `flushLayout()` throws `TypeError: Cannot set properties of null (setting 'font')` while `NumberSpinner` is present. Removed with a one-line comment at its removal site in the gallery array, per the plan's guidance not to chase environment-specific root causes.
- **The assertion asserts on `summary`, not on `duplicates.length` as the plan's Internal Structure snippet specified — because `duplicates.length` cannot fail.** Step 4's baseline run reported `duplicates.length === 25` against this gallery. That number is not a real duplicate-group count: `auditStyleRules()` caps its returned `duplicates` array to the top 25 rows (`MAX_ROWS` in `StyleAudit.ts`), and a throwaway uncapped tally (same grouping logic as `auditStyleRules()`, run inline in the test during baseline determination, then removed) found 36 real duplicate-body groups among the gallery's 117 `#id`-scoped rules — the gallery was already past the cap before this plan's assertion could ever see it move. An `expect(duplicates.length).toBeLessThanOrEqual(25)` assertion is therefore a tautology: `duplicates.length` cannot exceed 25 for *any* codebase state, so the test can never fail, in either direction — a fix that halved real duplication and a regression that doubled it would both leave the assertion green. This was caught by the audit's first round (BLOCKING #1/#2), which also flagged that the original note here incorrectly claimed the assertion would "catch a future fix that brings real duplication below 25" — `toBeLessThanOrEqual` never fails on a *decrease*, so that half was backwards too.

  The fix keeps everything else about the plan's approach (the gallery, `auditStyleRules()` as the only audit entry point, no change to `StyleAudit.ts`) and changes only what the test reads off the result: `StyleAuditResult.summary` (`StyleAudit.ts:70-76`) already exposes `componentRuleCount` (every `#id`-scoped rule) and `uniqueBodyCount` (distinct declaration bodies among them), both computed over the *full*, uncapped `entries` list rather than the sliced `duplicates` array. `componentRuleCount - uniqueBodyCount` is the count of `#id` rules beyond the first instance of each distinct body — i.e. every genuinely redundant rule, uncapped — and moves monotonically with real duplication in both directions. The test now asserts `redundantRuleCount <= STYLE_AUDIT_DUPLICATE_CEILING`, with the ceiling re-derived from this same worktree at 81 (`117 - 36`). This is a deviation from the plan's literal Internal Structure snippet, not from its intent or its Non-Goals — the plan's actual goal ("a regression ratchet on the live gallery's duplicate count") is now met, whereas the snippet as written was not.
