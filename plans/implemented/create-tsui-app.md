# `@jimka/create-tsui-app` Scaffolder — Implementation Plan

## Overview

Add a third workspace sibling, `packages/create-app/`, publishing the CLI package **`@jimka/create-tsui-app`**. Invoked as `npm create @jimka/tsui-app <target-dir>` (npm rewrites `create @jimka/tsui-app` → the `@jimka/create-tsui-app` package's `bin`), it writes a minimal, runnable typescript-ui starter to disk. The generated project's `package.json` declares `"@jimka/typescript-ui": "^0.1.0"` and installs it **from npm**.[^registry-live]

This plan sits on top of three others — the two below plus [`body-init-idiom.md`](plans/body-init-idiom.md), which makes `Body.init` the canonical mount the starter uses (see `## Architecture Decisions`). It consumes the npm-workspaces monorepo established by [`workspace-restructure.md`](plans/implemented/workspace-restructure.md) — the private root orchestrator ([package.json](package.json)) with its explicit `workspaces` array (`["packages/lib", "packages/docs"]`, restructure Step 6), whose Non-Goal bullet ([workspace-restructure.md:328](plans/implemented/workspace-restructure.md#L328)) reserves `packages/create-app` / `@jimka/create-tsui-app` as the third sibling this plan appends. The generated starter mirrors the `packages/docs` scaffold shape (restructure Steps 9–13). It mirrors [`publish-0-1-0.md`](plans/implemented/publish-0-1-0.md)'s scoped-public publish conventions (`publishConfig.access: public`) for publishing the scaffolder itself.

**Shared-file blast radius** (matching the `touches-shared` frontmatter): the root `package.json` gains `"packages/create-app"` in its `workspaces` array, `package-lock.json` is regenerated by the install that follows, and Phase 7 makes two additive documentation edits to the root `README.md` and `packages/lib/docs/guide/installation.md`. Everything else this plan writes is new files under `packages/create-app/`.

## Architecture Decisions

### The CLI never imports the library — it only writes files

The scaffolder writes template files to disk; the *generated project* is what depends on `@jimka/typescript-ui`. The CLI's own `dependencies` are therefore **empty** (zero runtime deps), and it always writes `^0.1.0` regardless of its own version.[^no-lib-import]

### Zero runtime dependencies — Node built-ins for args and prompts

Prompts and arg parsing use `node:util`'s `parseArgs` and `node:readline/promises` only.[^zero-deps] `vitest` is added as a **devDependency** for the unit tests; it does not ship and is not a runtime dep.

### Plain ESM JavaScript, no build step

The CLI is authored as plain ESM `.js`, like [packages/lib/scripts/llms/generate.mjs](packages/lib/scripts/llms/generate.mjs) — the repo's convention for Node tooling — **not** TypeScript-plus-build.[^plain-esm] Because the source is committed and shipped as-is, the scaffolder needs **no build guard**. The scoped-public `publishConfig` guard still applies.

### Templates are real files under `template/`, copied with a rename step

Starter files live as real files under `packages/create-app/template/` (not inlined heredocs), copied recursively to the target dir. The git-ignore file is stored as **`_gitignore`** and renamed to `.gitignore` on copy.[^gitignore-rename] The `files` array ships `template/` and `bin/` (plus `index.js`) so the published scaffolder actually contains its templates. The nested `template/package.json` is inert data, **not** a workspace member, because the root `workspaces` array lists packages explicitly (not via glob).

### The generated starter mirrors `packages/docs`, rendering one real component

The starter is the minimal Vite-app shape `packages/docs` establishes (`index.html` with `#app`, `src/main.ts`, `vite.config.ts`, `tsconfig.json`, `package.json`), minus the docs-only TypeDoc virtual-module plumbing and its `base` path. **Those files exist on disk** — read [packages/docs/package.json](packages/docs/package.json), [packages/docs/index.html](packages/docs/index.html), [packages/docs/vite.config.ts](packages/docs/vite.config.ts), [packages/docs/tsconfig.json](packages/docs/tsconfig.json), and [packages/docs/src/main.ts](packages/docs/src/main.ts) directly rather than reconstructing them from the restructure plan's steps.[^docs-precedent]

`src/main.ts` mounts via `Body.init({ layoutManager: Fit(), components: [Header('…')] })` — callable form, no `new` — rather than `Body.getInstance()` plus `addComponent`.[^body-init] `Fit` guarantees the single child fills the viewport, so the render is visibly correct without hardcoded sizes (leaning on library defaults per project conventions). This satisfies the same "import + render one real `@jimka/typescript-ui` component" requirement the restructure's docs `main.ts` step carries ([workspace-restructure.md:195](plans/implemented/workspace-restructure.md#L195)).

### The starter's `vite.config.ts` must preserve class/function names when minifying

The generated `vite.config.ts` **must** carry the same `build.rollupOptions.output.minify` keepNames block the library's own build configs use ([packages/lib/vite.config.ts:47-50](packages/lib/vite.config.ts#L47), [packages/lib/vite.lib.config.ts:93-96](packages/lib/vite.lib.config.ts#L93)), or `npm run build` produces a broken bundle.[^keep-names] This is encoded verbatim in the template with an explanatory comment.

### The scaffolder is itself publishable — scoped-public, executable bin

Mirror [publish-0-1-0.md](plans/implemented/publish-0-1-0.md)'s scoped-publish convention: `"publishConfig": { "access": "public" }`.[^scoped-public] The `bin` entry (`bin/create-tsui-app.js`) carries a `#!/usr/bin/env node` shebang and is committed with the executable bit set.

### Initial version `0.0.1`

The scaffolder versions **independently** of the library — its version says nothing about which library version it scaffolds. It ships as `0.0.1`.[^initial-version]

### Root `workspaces` array gains `packages/create-app`

Append `"packages/create-app"` to the root [package.json](package.json) `workspaces` array — the extension point the restructure reserved.[^workspaces-append] This is one of four shared files; the full blast radius is in `## Overview`. Do **not** touch the root `scripts`; the scaffolder's own scripts run via `npm -w packages/create-app run <script>`.

 * @returns {Promise<void>} Resolves once the starter is written.
 */
export async function scaffold(targetDir) { /* … */ }

/**

 * interface in a finally.
 * @returns {Promise<string>} The answer, trimmed.
 */
export async function promptForTargetDir() { /* … */ }

 * CLI entry: parse args, prompt when the directory is omitted, scaffold, then

## Internal Structure

`index.js` holds the pure helpers, the `scaffold` writer, and a `main`. `bin/create-tsui-app.js` is a thin executable wrapper:

```js
#!/usr/bin/env node
import { main } from '../index.js'
main(process.argv.slice(2)).catch((err) => { console.error(err.message); process.exit(1) })
```

`scaffold(targetDir)` steps (side-effectful):
1. Resolve `targetDir` to an absolute path; read its entries if it exists.
2. If it exists and `!isEmpty(entries)` → throw `Error('target directory "<dir>" is not empty')`.
3. `mkdir` recursive; recursively copy `template/` → target, computing each destination filename via `renameTemplateFile` (so `_gitignore` lands as `.gitignore`).
4. Post-process the copied `package.json`: parse it, set `name` = `toValidPackageName(basename(targetDir))`, write it back (the single template-variable substitution).

`scaffold` **writes only — it prints nothing.** All console output belongs to `main`.[^silent-scaffold]

`main(argv, ask = promptForTargetDir)`:

```js
const { targetDir } = parseCliArgs(argv)
const dir = targetDir ?? (await ask())      // prompt only when the positional was omitted
await scaffold(resolve(process.cwd(), dir)) // scaffold resolves/validates; main supplies the path
// then print next steps: `cd <dir>`, `npm install`, `npm run dev`
```

The prompt's answer and the parsed positional feed the same variable, so exactly one path reaches `scaffold`. Printing the next steps is `main`'s final act.

`promptForTargetDir()` wraps the single question. Use **`node:readline/promises`** and always close the interface:

```js
import { createInterface } from 'node:readline/promises'

export async function promptForTargetDir() {
    const rl = createInterface({ input: process.stdin, output: process.stdout })
    try {
        return (await rl.question('Project directory: ')).trim()
    } finally {
        rl.close()
    }
}
```

The `close()` in a `finally` is load-bearing, not tidiness.[^rl-close]

`main` takes the prompt as a **defaulted second parameter** so the unit test can pass a stub instead of driving a real TTY; the `bin` wrapper calls `main(argv)` and never supplies it.[^ask-seam]

The template dir is resolved relative to the module: `fileURLToPath(new URL('./template', import.meta.url))`.

## Expected Behaviour

**Unit-testable (pure helpers — [packages/lib/tests/unit/llms-generate.test.ts](packages/lib/tests/unit/llms-generate.test.ts) style):**

- **`toValidPackageName`** applies the npm name rules in this order: lowercase, trim, replace whitespace and invalid characters with `-`, then strip a leading `.` or `_` and any leading or trailing `-`. Each row below is a test case:

  | Input | Output | Rule exercised |
  |---|---|---|
  | `"My App"` | `"my-app"` | lowercase + whitespace → `-` |
  | `"Foo/Bar"` | `"foo-bar"` | invalid character → `-` |
  | `"_x"` | `"x"` | leading `_` stripped |
  | `".foo"` | `"foo"` | leading `.` stripped |
  | `"-my-app-"` | `"my-app"` | leading and trailing `-` stripped |
  | `"My App!"` | `"my-app"` | trailing `-` from the replaced `!` is stripped too |
  | `"my-app"` | `"my-app"` | already valid, passes through unchanged |

  The last two rows matter most: replacement runs *before* the strip, so a trailing invalid character becomes a `-` and is then removed rather than surviving as `"my-app-"`.
- **`renameTemplateFile`** maps `"_gitignore"` → `".gitignore"` and returns every other name unchanged (`"index.html"` → `"index.html"`, `"package.json"` → `"package.json"`). No other name is rewritten.
- **`isEmpty`** is `true` for `[]` and `false` for any non-empty entry list (`["index.html"]` → `false`).
- **`parseCliArgs`** returns `{ targetDir: "my-app" }` for `["my-app"]` and `{ targetDir: undefined }` for `[]`.

**Unit-testable (`scaffold` against a real temp dir — `fs.mkdtempSync(join(tmpdir(), 'create-tsui-app-'))`, removed in an `afterEach`):**

These touch only the filesystem — no registry access is involved, so they are automated tests, not manual steps.

- **Target directory does not exist yet (the primary path).** `scaffold(join(tmp, 'my-app'))` where `my-app` has not been created **creates it** (`mkdirSync` recursive) and writes the starter into it. This case must construct a path that does not exist.[^primary-path]
- **Refuse-if-nonempty.** `scaffold` on an existing non-empty dir rejects with `target directory … is not empty` and writes nothing (assert the pre-existing entry is still the directory's only content).
- **Rename applied on disk.** After scaffolding into an empty temp dir, the output contains `.gitignore` (from `_gitignore`) and no file literally named `_gitignore`.
- **Name substitution.** The generated `package.json` `name` equals `toValidPackageName(basename(targetDir))`, and its `dependencies["@jimka/typescript-ui"]` is `"^0.1.0"`.
- **Template copied whole.** Every file under `template/` has a counterpart in the output (modulo the rename), including nested `src/main.ts` — proving the recursive walk descends into subdirectories.

**Unit-testable (`main` — the prompt seam):**

- **Prompt when the directory is omitted.** `main([])` asks once and scaffolds into the answer; `main(['my-app'])` scaffolds without prompting and never calls the prompt. Unit-test by passing a stub as `main`'s second argument (`main([], async () => tmpDir)`) — the `ask` parameter documented in `## Internal Structure` is the seam; do **not** reach for `vi.mock` or module-level indirection. The stub must return an **absolute** path, since `main` resolves against `process.cwd()` and a relative answer would write into the repo.[^prompt-coverage]

Note this covers *which* path `main` takes, not whether the readline interface is closed afterwards — the stub replaces readline entirely. Interface closure is only observable on a real TTY (`## Verification`, interactive-path check).

**Manual / integration (needs the network or a browser):**

- **Published-tarball surface.** `npm pack` of the scaffolder includes `index.js`, `bin/`, and `template/**` (with `template/_gitignore`); publish access is public.
- **Registry install + build (scriptable, required).** In a scaffolded app: `npm install` resolves `^0.1.0` from the registry, `npm run build` exits 0, and `dist/index.html` exists.
- **The scaffolded project typechecks (scriptable, required).** `npm run typecheck` (`tsc --noEmit`) exits 0 in the generated app.
- **Rendered page (manual).** `npm run dev`, open the page: the `Header` renders and the console is clean — UI/geometry, not automatable here.

## Notes

[^registry-live]: `@jimka/typescript-ui@0.1.0` is live on the public registry — confirm with `npm view @jimka/typescript-ui version`, which is the authority here; [publish-0-1-0.md](plans/implemented/publish-0-1-0.md) records the procedure but not the outcome. So the generated project's `^0.1.0` range resolves and the whole scaffold → install → build path is runnable today. That is why the registry-install checks (Phase 5) are required scriptable steps rather than deferred or manual ones.

[^no-lib-import]: This is the standard `create-*` shape — Vite's `create-vite` ships templates as data and imports nothing from the framework. Keeping the CLI's runtime dependency list empty makes the published scaffolder tiny and framework-version-agnostic: the library version it writes is a constant in the template, not a function of the scaffolder's own version.

[^zero-deps]: Precedent: the repo's Node tooling is written as plain zero-dep ESM scripts ([packages/lib/scripts/llms/generate.mjs](packages/lib/scripts/llms/generate.mjs), [packages/lib/scripts/eslint/*.mjs](packages/lib/scripts/eslint)). There is no prompt library anywhere in the workspace — verified across the root, [packages/lib/package.json](packages/lib/package.json), and [packages/docs/package.json](packages/docs/package.json) (no `prompts`/`inquirer`/`enquirer`). The root declares no `devDependencies` at all, so checking the root alone would be vacuous — the per-package manifests are where the evidence is. Adding a prompt library would introduce a precedent the repo does not have, and the only interaction needed is "ask for the target dir when omitted" — a single `readline` question.

[^plain-esm]: A published `create-*` bin must run directly via `node` the moment npm fetches it. A build step would add a `prepublishOnly` compile and a gitignored `dist`. `packages/lib` needs its `prepublishOnly` build guard (see [publish-0-1-0.md](plans/implemented/publish-0-1-0.md)) only because its `dist/lib` is gitignored; committed-and-shipped source has no equivalent hazard.

[^gitignore-rename]: npm **force-excludes** a file literally named `.gitignore` from every published tarball regardless of the `files` array, so a template shipped as `.gitignore` would silently vanish from the published package. Storing it as `_gitignore` and renaming on copy is the standard workaround, and the same convention `create-vite` uses.

[^docs-precedent]: `packages/docs` is the closest precedent available: it is a *consumer app* rather than the library build, which is also what makes its keepNames guard the right one to copy. Reading the real files avoids reconstructing a scaffold from a plan's prose and drifting from what is actually on disk.

[^body-init]: Every existing mount in the tree uses `Body.getInstance()` + `addComponent` — [packages/docs/src/main.ts:8](packages/docs/src/main.ts#L8), [packages/lib/src/typescript/main.ts:40](packages/lib/src/typescript/main.ts#L40), and ten published doc pages. So the starter diverges from the established pattern, and not because of a convention mandate: `CODE_CONVENTIONS.md`'s options-bag rule does **not** cover this case, since it governs construction (`new Button({ text })` over `b.setText(text)`), whereas `getInstance()` is a singleton accessor and `addComponent` is not a setter. The divergence rests instead on a project decision to make `Body.init` the canonical mount. `init` is real, tested ([packages/lib/tests/core/Body.test.ts:26](packages/lib/tests/core/Body.test.ts#L26)), and self-documented as "the ergonomic entry point for mounting a top-level layout in one call" ([packages/lib/src/typescript/lib/core/Body.ts:32-44](packages/lib/src/typescript/lib/core/Body.ts#L32)), but has zero production call sites because the docs predate it. That migration is owned by [body-init-idiom](plans/body-init-idiom.md), not this plan — a scaffolder should not also carry a documentation migration — and this plan `depends-on` it so the starter never ships an idiom the published docs contradict.
    The callable form (`Fit()`, `Header(...)`, no `new`) is the repo-wide idiom: [packages/lib/llms.txt:8](packages/lib/llms.txt#L8) states the "callable + options-bag idiom", [packages/lib/docs/guide/index.md:26](packages/lib/docs/guide/index.md#L26) tells users "`Window('Hello')` works without `new`", [plans/implemented/callable-docs-sweep.md](plans/implemented/callable-docs-sweep.md) swept `new X(` → `X(` across the docs with both `Fit` and `Header` on its allowlist, and `Body.ts:35`'s own example is `Body.init({ layoutManager: Fit(), components: [shell] })`. Writing `new` here would contradict every published example in the one file a new user reads first.

[^keep-names]: typescript-ui derives every component's CSS class (and layout-serialization keys) from `this.constructor.name`. If the production minifier mangles class names, `constructor.name` returns a short or empty string and `classList.add("")` throws, blanking the built page. Vite 8 (Rolldown/oxc) minifies by default, so an unguarded generated config produces a broken bundle on the user's first `npm run build`.

[^scoped-public]: Scoped packages default to restricted access. Baking `publishConfig.access: public` into the manifest avoids a forgotten `--access public` on the publish command.

[^initial-version]: `0.0.1` marks the package honestly as a brand-new, minimal, unproven first cut, decoupled from the library's `0.1.0` line. `0.1.0` was rejected: it would falsely imply lock-step with the library's version, which the scaffolder does not track.

[^workspaces-append]: The append is safe because `depends-on` sequences this plan after `workspace-restructure`, so `packages/create-app` exists on disk by the time `npm install` reads the `workspaces` array.

[^silent-scaffold]: Keeping `scaffold` output-free lets the temp-dir unit tests call it without spewing CLI text into the test run.

[^rl-close]: An open readline interface keeps stdin referenced, so the process **hangs after printing the next steps and never exits** — the CLI appears to work, then just sits there. The `finally` guarantees the close runs even if the question rejects. Using `node:readline/promises` rather than the callback API also avoids hand-wrapping the question in a Promise.

[^ask-seam]: This is the minimum seam that makes the prompt path testable; it introduces no abstraction beyond one injectable default.

[^metadata-before-publish]: npm renders `keywords`/`author`/`repository`/`homepage`/`bugs` on the package page, and a published version is immutable — `0.0.1` can never be amended, only superseded by `0.0.2`. Same reason the README must exist before the publish.

[^tool-versions-in-lib]: The root manifest is a pure orchestrator and declares no `devDependencies`, so `packages/lib` is where the repo's tool versions are pinned and the version to match.

[^no-cpsync]: `fs.cpSync`'s recursive mode has no per-entry rename hook — its `filter` option can only include or exclude an entry, never rewrite the destination name — so it cannot apply the `_gitignore` → `.gitignore` rename this plan depends on. A manual recursive walk is the only way to get the rename.

[^allow-positionals]: Without `allowPositionals: true`, `parseArgs` throws `Unexpected argument '<dir>'. This command does not take positional arguments` for every invocation that supplies a target directory — that is, the entire happy path.

[^license-and-readme]: npm includes `LICENSE` and `README.md` in every tarball regardless of the `files` array, and [packages/lib](packages/lib) carries both as the repo's one published-package precedent ([publish-0-1-0.md:11](plans/implemented/publish-0-1-0.md#L11) records copying *both* in before publishing). A package declaring `"license": "PolyForm-Noncommercial-1.0.0"` must ship the licence *text*, not merely the field, since a non-OSI licence's terms are not inferable from its SPDX identifier alone. npm renders the package-root README as the package page, so publishing without one would leave `0.0.1` permanently blank on npm, fixable only by burning `0.0.2`.

[^template-typescript]: `packages/docs` gets away with shipping a `tsconfig.json` and `.ts` sources without a `typescript` devDependency only because `typescript ^6.0.3` is hoisted from [packages/lib/package.json](packages/lib/package.json) inside this monorepo. A scaffolded project lives outside the workspace and inherits nothing, so without the explicit devDependency the template's `"strict": true` is never enforced and `npx tsc --noEmit` fails out of the box. `vite build` would still pass, because Vite transpiles TypeScript without type-checking it — which is also why the generated app needs its own `typecheck` script and why the typecheck check cannot be folded into the registry-install check.

[^skip-lib-check]: The generated project actually *runs* `tsc --noEmit` via its `typecheck` script. Without `skipLibCheck`, TypeScript type-checks every `.d.ts` under `node_modules` — Vite's own plus `@jimka/typescript-ui`'s `dist/lib/types/**` — and a third-party declaration error would fail a freshly scaffolded project out of the box. `packages/docs` omits the flag safely only because nothing ever runs `tsc` there.

[^phase3-before-tests]: `npm -w packages/create-app run test` cannot work until the workspace is registered and `npm install` has put `vitest` on disk; running it earlier fails with an unrecognised-workspace error.

[^publish-token]: A plain npm login is rejected with `E403 … Two-factor authentication or granular access token with bypass 2fa enabled is required`. Also note the registry's read path can lag a successful `PUT` by several minutes, so a transient 404 from `npm view` immediately after publishing is not a failure.

[^phase7-after-publish]: These edits advertise `npm create @jimka/tsui-app`, which resolves `@jimka/create-tsui-app` from the registry and therefore 404s until the package is published.

[^primary-path]: Creating the directory is a *different branch* from the exists-and-empty cases below, and it is what `npm create @jimka/tsui-app my-app` actually does. Seeding the target with `mkdtempSync` exercises only the exists-and-empty path, so this case would silently go uncovered.

[^prompt-coverage]: The prompt is the only interactive behaviour in the package and the sole thing the zero-dep-prompt decision rests on, so it must not go unverified.

[^lib-readme-untouched]: `packages/lib/README.md` ships in the library tarball and describes the library, not its tooling; the scaffolder documents itself via its own `packages/create-app/README.md` on npm. The root `README.md` and the published `packages/lib/README.md` are different files, not a symlink.

[^no-root-scripts]: A consequence of leaving root `scripts` alone: the scaffolder's tests run only via `npm -w packages/create-app run test`, never from a root aggregate command, and CI runs no tests at all today. Accepted, not overlooked.

[^prompt-tty]: Piping stdin cannot detect a missing `rl.close()`. With piped input the stream reaches EOF, readline emits `close` on its own, and the process exits 0 whether or not the code closed the interface — so `printf 'x\n' | node bin/…` under a timeout passes unconditionally and verifies nothing. The hang requires a stdin that stays open, which is why this check needs a real terminal and cannot be scripted in CI.

  codebase's existing solution wins wherever a plan leaves or creates a
  conflict. The scaffold tests assert `index.html` exists, not its contents, so
  they are unaffected.
- **`toValidPackageName`** was implemented as: lowercase + trim, replace any
  character outside `[a-z0-9._-]` (i.e. whitespace and other invalid characters)
  with `-`, strip a leading run of `.`/`_`, then strip leading/trailing `-`. This
  preserves interior `.`/`_` (only stripping them when leading), matching the
  step-2 spec's literal wording more closely than a first draft that mapped
  every `.`/`_` to `-` unconditionally; both drafts pass all seven `##
  Expected Behaviour` table rows, since none of them exercises an interior
  `.`/`_`.
- **The `### Initial version 0.0.1` decision (lines 50-52) and its
  `[^initial-version]` footnote (line 538) were reversed after this plan
  shipped.** Commit `f19c076c` bumped the scaffolder from `0.0.1` to `0.3.0`
  alongside the library, and every release since has kept the two locked;
  `release-steps.md` now codifies the lock instead of independent versioning.
  npm versions cannot go backwards, so restoring independence is not an
  available option — the lock is recorded here rather than reverted.
