# Docs Sidebar — Section Index Nodes and API Kind Grouping — Implementation Plan

## Overview

Three structural changes to the docs app's sidebar tree, plus a content pass over the seven authored `index.md` files.

1. **A section's index page moves onto its branch node.** Today `Guide` is a branch with a leaf child `Introduction` pointing at `/guide`. After this change the `Guide` branch node itself opens `/guide` and the leaf is gone. The remaining children are then sorted alphanumerically. This touches `NavGroup` and `getNav` in [`packages/docs/src/content/pages.ts:26`](packages/docs/src/content/pages.ts#L26), `buildGroupNode` in [`packages/docs/src/shell/DocsSidebar.ts:97`](packages/docs/src/shell/DocsSidebar.ts#L97), and the nav↔glob bijection test in [`packages/docs/tests/pages.test.ts:147`](packages/docs/tests/pages.test.ts#L147).

2. **The generated API tree gains its kind directories as real levels.** `core > Classes > Component` instead of `core > Component`. The nav tree stops being derived from `typedoc-sidebar.json`'s categories in [`packages/docs/vite.config.ts:90`](packages/docs/vite.config.ts#L90) and is derived instead from the emitted file list `apiFiles`, inside [`packages/docs/src/content/api.ts`](packages/docs/src/content/api.ts).

3. **Every module's index page is generated by the app, grouped by kind.** The app stops rendering TypeDoc's generated module index pages and renders a page built from the same directory-and-kind layout the tree is built from, so page and tree agree. That covers all nineteen module nodes — `core`, `data`, `layout`, `overlay`, `primitive`, `router`, `validation`, the eleven `component/*` modules, and the `component` group node, which has no generated page at all. The transform functions live beside [`normalizeApiMarkdown`](packages/docs/src/content/apiMarkdown.ts#L20).

`typedoc-sidebar.json` stops being read at all: the status bar's two counts are derived from `apiFiles` too, and the virtual module `virtual:typedoc-api` is reduced to a single `apiFiles` export.

No library TypeScript changes — the only `packages/lib` edits are to authored Markdown under `packages/lib/docs/`. `packages/lib/typedoc.json` is untouched.

## Architecture Decisions

### Reversal — section children are sorted, but labels stay hand-authored

`plans/implemented/docs-content-migration.md` decided "the nav table stays hand-authored", keeping both the labels and the `config.mts` ordering. This plan reverses the ordering half only: each group's children are sorted alphanumerically by label. The labels themselves keep coming from the hand-authored table for exactly the reason that plan's `[^hand-authored-labels]` footnote gives.[^ordering-reversal]

### Reversal — API kind directories become tree levels

`plans/implemented/docs-typedoc-reference.md`'s `[^flatten-categories]` footnote justified flattening partly on "flattening preserves TypeDoc's ordering — classes, then interfaces, then type aliases — which is the part of the grouping readers actually use". That claim is reversed: the kind grouping becomes an explicit tree level rather than an implicit ordering.[^kind-reversal]

### The API nav tree is derived from `apiFiles`, not from `typedoc-sidebar.json`

`buildApiNav` / `flattenItems` / `routeFromLink` in `vite.config.ts` are deleted, along with the `apiNav` export of the `virtual:typedoc-api` module. `api.ts` gains `buildApiNav(files)`, which builds the tree from the `apiFiles` path list that the same virtual module already exports.[^derive-from-files]

### The status bar's two counts are derived from `apiFiles` as well

`readSidebar`, `countMatching`, `isModuleLink`, `isSymbolLink` and the `SIDEBAR_JSON` constant are deleted from `vite.config.ts`. `api.ts` gains `moduleCount()` and `symbolCount()`, computed from `apiFiles`, and `DocsShell` imports them from there.[^counts-in-api]

| Count | Definition over `apiFiles` | Value today |
|---|---|---|
| `symbolCount()` | files whose name is not `index.md` | 683 |
| `moduleCount()` | files ending `/index.md` whose path does not contain `/namespaces/` | 18 |

Both numbers are unchanged from what `typedoc-sidebar.json` yields today, so the status bar still reads `18 modules · 683 documented symbols`.[^counts-match]

### Every module index page is synthesized on the kind axis; namespace index pages are not

The app renders a generated page for all nineteen module nodes, listing each module's symbols under a `## ` heading per reflection kind — the same six or seven groups the tree now shows under that module. TypeDoc's generated module index pages are left on disk and still copied into `dist/api/`; the app simply never renders them.[^synthesize-all]

**The authored `@category` grouping stops surfacing anywhere in the app.** `core/index.md`'s `## Core` / `## Data` / `## Theme` / `## Util` / `## Other` sections, and the `categoryOrder` list in `packages/lib/typedoc.json` that orders them, become invisible to a reader of the docs app. That cost is accepted so that a module's page and the tree beside it are organized on one axis instead of two.[^two-axes]

Namespace index pages (`core/namespaces/Animation/index.md` and the five others) are **excluded** — they are fetched and rendered exactly as today. A namespace index carries the namespace's own doc comment and `## Remarks` prose above its symbol lists; a synthesized page cannot reproduce that. A module index carries no prose at all.[^namespace-exclusion]

### One ordering rule for the whole sidebar: branches first, then leaves, each alphanumeric

This is the rule [`sortApiNodes`](packages/docs/src/content/api.ts#L103) already applies to the generated tree; the authored sections now follow it too. The shared comparator moves to a new `packages/docs/src/content/labelOrder.ts` and both sides import it.[^shared-comparator]

| Level | Children | Order |
|---|---|---|
| `Layouts` | groups `Layout managers`, `Docking`, `Serialization`; page `Constraints` | Docking, Layout managers, Serialization, Constraints |
| `Guide` | pages `Installation`, `Mental model` | Installation, Mental model |
| `Concepts` | pages incl. `Data binding`, `DOM seams` | …, Data binding, DOM seams, Events, … |
| `/api` root | `component`, `core`, `data`, `layout`, `overlay`, `primitive`, `router`, `validation` | unchanged (all branches, already alphabetical) |
| `/api/core` | `Classes`, `Functions`, `Interfaces`, `Namespaces`, `Type Aliases`, `Variables` | as listed (all branches) |

`sortApiNodes` survives unchanged. Its branches-before-leaves half becomes inert on the API side, because every level of the new tree is homogeneous — a module's children are all kind directories, a kind directory's children are all leaves.[^sort-survives]

### `sensitivity: 'base'` puts `Data binding` before `DOM seams`

The comparator is `localeCompare(b, undefined, { numeric: true, sensitivity: 'base' })` — the same options `sortApiNodes` uses today.

| A | B | Winner | Why |
|---|---|---|---|
| `Data binding` | `DOM seams` | `Data binding` | case-insensitive: `da` < `do` |
| `Component lifecycle` | `Constructing components` | `Component lifecycle` | `com` < `con` |
| `Layering` | `Layout system` | `Layering` | `laye` < `layo` |
| `Foo2` | `Foo10` | `Foo2` | `numeric: true` |

### The kind level is labelled from a fixed display map

A directory whose name is one of TypeDoc's seven kind directories renders with a display label; any other directory name is used verbatim, so module and namespace names keep their exact casing.[^kind-label-map]

| Directory | Node label |
|---|---|
| `classes` | `Classes` |
| `enumerations` | `Enumerations` |
| `functions` | `Functions` |
| `interfaces` | `Interfaces` |
| `namespaces` | `Namespaces` |
| `type-aliases` | `Type Aliases` |
| `variables` | `Variables` |
| `core` | `core` |
| `button` | `button` |
| `Animation` | `Animation` |

### The synthesis is plugged in at `apiFileFor` / `fetchApiPage`

`DocsContent` needs no change at all. Every module route resolves to a file name exactly as it does today — `apiFileFor('/api/core')` returns `core/index.md`, `apiFileFor('/api/component')` returns the *notional* file `component/index.md` — and `fetchApiPage` recognises those nineteen names and returns generated Markdown instead of fetching.[^sentinel-file]

Routing stays unambiguous because the synthesis changes only *what is returned for* a file name, never *which* file name a route maps to. `apiRouteFor` and `apiDirOf` are untouched, and `apiDirOf('core/index.md') === 'core'` is exactly the base directory the synthesized page's relative links are written against.

### The data-layer stack list in `data/index.md` is not sorted

Every other bulleted link list under a heading in the seven authored `index.md` files is sorted. `data/index.md`'s first list (Model → Proxy → Store → ModelRecord → Association → Binding) is left alone: it is prose walking through the ASCII diagram directly above it, not an index of pages.[^stack-list]

## Internal Structure

### Deriving the API tree from `apiFiles` (`api.ts`)

`apiFiles` is the recursive, sorted list of every `.md` file under `packages/lib/docs/api`, relative to it. The tree is a directory trie over those paths.

| `apiFiles` entry | Node position | Node `path` |
|---|---|---|
| `index.md` | *skipped* — it is the API Reference root's own page, which `DocsSidebar` supplies as `API_PREFIX` | — |
| `core/index.md` | `core` | `/api/core` |
| `core/classes/Component.md` | `core > Classes > Component` | `/api/core/classes/Component` |
| `core/interfaces/PanelOptions.md` | `core > Interfaces > PanelOptions` | `/api/core/interfaces/PanelOptions` |
| `core/type-aliases/Handle.md` | `core > Type Aliases > Handle` | `/api/core/type-aliases/Handle` |
| `core/namespaces/Animation/index.md` | `core > Namespaces > Animation` | `/api/core/namespaces/Animation` |
| `core/namespaces/Animation/functions/play.md` | `core > Namespaces > Animation > Functions > play` | `/api/core/namespaces/Animation/functions/play` |
| `component/button/index.md` | `component > button` | `/api/component/button` |
| *(no file)* | `component` | `/api/component` — synthesized |
| *(no file)* | `core > Classes` | `null` — grouping only |

Rules:

- A file named `index.md` sets its **containing directory node's** `path`; it never becomes a child node.
- Any other file becomes a leaf node, labelled with its filename minus `.md`.
- A directory node's label is `KIND_LABELS[name] ?? name` (table above).
- A directory node with no `index.md` and no synthesized index has `path: null`. Clicking it does nothing — `DocsSidebar.onSelection` already ignores a node with no `data`.

`api.ts` holds the sorted tree in one module-level constant and a lookup map, in this declaration order:

```typescript
const FILES              = new Set(apiFiles);
const KIND_LABELS        : Record<string, string>;
export const MODULE_INDEX_FILES : Set<string>;          // the nineteen index files the app synthesizes
const API_NAV            : ApiNavNode[] = sortApiNodes(buildApiNav(apiFiles));
const NAV_BY_PATH        : Map<string, ApiNavNode>;     // every node with a non-null path, keyed by that path
```

`getApiNav()` returns `API_NAV`. Building the tree once means the synthesized pages and the sidebar can never disagree about a module's contents or their order.

### Which index files the app synthesizes (`api.ts`)

`MODULE_INDEX_FILES` is derived from `apiFiles`, never hard-coded. For every file, walk its directory chain; a directory is a **module directory** when **both** hold:

- no segment of its path is `namespaces`, and
- its last segment is not a key of `KIND_LABELS`.

`MODULE_INDEX_FILES` is then `<module directory>/index.md` for each one.

| Directory | Module directory? | Why |
|---|---|---|
| `core` | yes | no `namespaces` segment; `core` is not a kind |
| `core/namespaces` | no | last segment `namespaces` is a kind |
| `core/namespaces/Animation` | no | contains a `namespaces` segment |
| `core/namespaces/Animation/functions` | no | contains a `namespaces` segment |
| `component/button` | yes | no `namespaces` segment; `button` is not a kind |
| `component/button/classes` | no | last segment `classes` is a kind |

Today that yields exactly nineteen entries: `component/index.md`, the eleven `component/*/index.md`, and `core` / `data` / `layout` / `overlay` / `primitive` / `router` / `validation`. Eighteen of the nineteen exist on disk; `component/index.md` does not. Note `router` is a real module — its entry point was added to `typedoc.json` before this plan was written — so it is easy to omit when listing the top-level modules by hand; the rule derives the set from `apiFiles` and picks it up automatically.[^no-component-index]

`MODULE_GROUPS` is the separate, smaller list used by the root-index collapse: every **first-level** module directory with no real `index.md` in `FILES`. Today that is `['component']`.

Wiring:

- `apiFileFor` accepts `<rest>/index.md` when it is in `FILES` **or** in `MODULE_INDEX_FILES`.
- `fetchApiPage(file)` returns the synthesized page immediately when `file` is in `MODULE_INDEX_FILES`, with no network request.
- `fetchApiPage('index.md')` additionally applies `collapseModuleGroups(source, MODULE_GROUPS)` after `normalizeApiMarkdown`.

### Building a module's sections (`api.ts`)

Each module node's children split cleanly by `path`: a kind directory has `path === null`, a submodule has a `path`. Kind directories become one section each, headed by the kind's display label; submodules are collected into a single `Modules` section, headed like TypeDoc's own root index.

```typescript
function moduleSections(node: ApiNavNode, dir: string): IndexSection[] {
    const kinds = node.children.filter((child) => child.path === null);
    const subs  = node.children.filter((child) => child.path !== null);
    const link  = (child: ApiNavNode, text: string): { text: string; href: string } =>
        ({ text, href: apiFileFor(child.path!)!.slice(dir.length + 1) });

    return [
        ...(subs.length > 0
            ? [{ heading: 'Modules', links: subs.map((child) => link(child, child.label)) }]
            : []),
        ...kinds.map((kind) => ({
            heading: kind.label,
            links:   kind.children.map((child) => link(child, child.label)),
        })),
    ];
}
```

The `slice(dir.length + 1)` drops the module directory prefix, which makes every href relative to the page's own directory. The link text is always the child's own label, unprefixed — a submodule's `component/` prefix would be redundant on a page the reader is already inside `component` to reach:

| Module `dir` | Child node `path` | `apiFileFor` | Emitted href | Link text |
|---|---|---|---|---|
| `core` | `/api/core/classes/Component` | `core/classes/Component.md` | `classes/Component.md` | `Component` |
| `core` | `/api/core/namespaces/Animation` | `core/namespaces/Animation/index.md` | `namespaces/Animation/index.md` | `Animation` |
| `component` | `/api/component/button` | `component/button/index.md` | `button/index.md` | `button` |
| `component/button` | `/api/component/button/classes/Button` | `component/button/classes/Button.md` | `classes/Button.md` | `Button` |

Because the sections are read off `API_NAV`, which is already sorted, the page's sections and each section's links come out in the same order as the tree — no second sort.

### Rendering a synthesized page (`apiMarkdown.ts`)

`moduleIndexSource` writes the breadcrumb, the `# ` heading and the sections. The breadcrumb's `..` count is the module path's segment count, so it points at the root `index.md` from any depth.

| `module` | Breadcrumb line | Heading |
|---|---|---|
| `core` | `[@jimka/typescript-ui](../index.md) / core` | `# core` |
| `component` | `[@jimka/typescript-ui](../index.md) / component` | `# component` |
| `component/button` | `[@jimka/typescript-ui](../../index.md) / component/button` | `# component/button` |

These are byte-identical to the first three lines of the corresponding generated file, where one exists. Only the section headings below them change — from `@category` names to kind names.

`moduleIndexSource('core', …)` produces:

```markdown
[@jimka/typescript-ui](../index.md) / core

# core

## Classes

- [AnimatedDropdown](classes/AnimatedDropdown.md)
- [Aria](classes/Aria.md)
…

## Functions

…

## Namespaces

- [Animation](namespaces/Animation/index.md)
…
```

and `moduleIndexSource('component', …)`:

```markdown
[@jimka/typescript-ui](../index.md) / component

# component

## Modules

- [button](button/index.md)
- [chart](chart/index.md)
…
- [tree](tree/index.md)
```

A section with no links still emits its heading; a module with no sections emits breadcrumb and heading only.

### The root index collapse

`collapseModuleGroups(source, ['component'])` replaces the run of eleven lines

```markdown
- [component/button](component/button/index.md)
…
- [component/tree](component/tree/index.md)
```

with the single line

```markdown
- [component](component/index.md)
```

at the position of the first matched line. A source with no matching line is returned byte-identical.

### Sorting `getNav`'s output (`pages.ts`)

At the end of `getNav`, before `return nav`, run a recursive pass that sorts each group's `pages` by `label` and its `groups` by `title`, using `compareLabels`. The arrays are freshly built literals on every call, so sorting them in place is safe.

The branches-before-leaves half of the rule is applied by the renderer: `DocsSidebar.buildGroupNode` emits `groups` before `pages` (today it emits `pages` first).

## Notes

[^ordering-reversal]: The original decision bundled two things: *where labels come from* and *what order entries appear in*. The label half stands — `config.mts` remains the authoritative label source, because three page headings differ from their sidebar title and one leaks backticks into a plain tree label. The ordering half only made sense while each section's index page was pinned first as `Introduction` / `Overview` / `Catalog`; alphabetising would have buried it mid-list. Once the index page moves onto the branch node, nothing is left that depends on position, and 91 component entries in transcription order are harder to scan than the same 91 sorted.

[^kind-reversal]: The `docs-typedoc-reference` plan's own addendum already walked back half of this footnote: kind-order put `Button`, `MenuButton` and `SplitButton` ahead of `ButtonEvent` and `ButtonOptions`, so `getApiNav` gained an alphanumeric sort — which destroyed the implicit kind grouping entirely, since sorting mixes classes and interfaces together. That left readers with neither the grouping nor the ordering. Making the kind directories explicit levels restores the grouping *and* keeps the alphabetical sort, because sorting now happens within a homogeneous level.

[^two-axes]: A symbol has two independent groupings. Its `@category` (`Core` / `Data` / `Theme` / `Util` / `Other`) is authored in a JSDoc tag and drives the `## ` headings on the generated module index page and the second level of `typedoc-sidebar.json`. Its reflection kind (`classes` / `interfaces` / `type-aliases` / `functions` / `variables` / `enumerations` / `namespaces`) is intrinsic and drives the on-disk directory layout. Once the tree groups by kind, keeping the page grouped by category would put a differently-organized list of the same symbols next to the tree. Kind wins because it partitions every module into evenly-sized, predictable runs, while 11 of the 18 modules have a single category plus a leftover `Other`. Restoring categories as tree levels instead was rejected for the same reason.

[^derive-from-files]: Three reasons over transforming the category tree. First, the kind level is a property of the file path, so deriving it from the sidebar JSON would mean re-parsing each `link` to recover the directory anyway. Second, `apiFiles` is already exported and already the source of truth for `apiFileFor`, so nav and content resolution stop being able to disagree. Third, `api.ts` is unit-tested under Vitest (which resolves `virtual:typedoc-api` through this same `vite.config.ts`), while the config's plugin functions are not — moving the derivation into `api.ts` moves it under test.

[^counts-in-api]: Same argument as the nav tree, applied to the last two consumers of `typedoc-sidebar.json`. Keeping the counts in `vite.config.ts` would mean keeping `readSidebar`, `SidebarItem`, `countMatching`, `isModuleLink` and `isSymbolLink` alive for four lines of arithmetic, and would leave two independent descriptions of "what a module is" in the codebase — one over sidebar links, one over file paths. Moving them into `api.ts` puts them under Vitest, reduces `virtual:typedoc-api` to a single export, and lets the file-path definition be the only one.

[^counts-match]: Measured against the freshly generated tree: 708 `.md` files, 25 of them named `index.md`, so 683 symbol pages — which is what the status bar shows today. Of those 25, one is the root `index.md` (which does not end `/index.md`) and six are namespace indexes (which contain `/namespaces/`), leaving 18 module indexes — also what the status bar shows today. Count from the tree rather than trusting a figure quoted in an earlier plan: `docs-typedoc-reference` recorded 696 files and 24 indexes, and that tree has since grown. The synthesized `component/index.md` is not in `apiFiles`, so it does not inflate `moduleCount`, which is correct: `component` is a grouping node, not a TypeDoc module.

[^synthesize-all]: Synthesizing only `component`'s index — the one module node with no generated page — would leave the app rendering eighteen category-grouped pages beside a kind-grouped tree, and one kind-grouped page beside the same tree. Synthesizing all nineteen costs nothing extra: the same function, the same section builder, and the tree data it reads is already built. The generated files are left on disk rather than excluded from the `dist/api/` copy so that the copy step stays a plain recursive `cpSync` and a deep link straight to a generated file still resolves.

[^namespace-exclusion]: `core/namespaces/Animation/index.md` opens with a paragraph ("Small helpers for playing CSS transitions on raw DOM elements.") and a `## Remarks` block before its `## Core` / `## Other` lists — the namespace's own doc comment, which exists nowhere in `apiFiles` and cannot be reconstructed from paths. Every one of the eighteen generated *module* index pages, by contrast, is exactly breadcrumb / blank / `# name` / blank / category lists, with no prose to lose. So the cost of synthesizing is zero for modules and a lost doc comment for namespaces.

[^no-component-index]: `component` has no `index.md` because `typedoc.json` declares entry points named `component/button`, `component/chart`, … — TypeDoc treats the slash as part of the module name and never materialises a `component` module. The predicate that finds it is derived from the file tree rather than hard-coded to `'component'`, so a future grouped entry-point set (`chart/line`, say) needs no code change.

[^shared-comparator]: The comparator is four tokens of configuration whose exact options are load-bearing (`numeric` for `Foo2` before `Foo10`, `sensitivity: 'base'` so a lowercase function name interleaves with class names). Duplicating it in `pages.ts` invites the two sidebars drifting apart. A one-function module matches the existing shape of `content/` — `containers.ts`, `notFound.ts` and `apiMarkdown.ts` are all small single-purpose modules with their own tests.

[^sort-survives]: Before this change, a module's children were a mix of namespace branches and symbol leaves, so branches-first did real work. Afterwards, a module's children are only kind directories (all branches), a kind directory's children are only symbol pages (all leaves), and `Namespaces` contains only namespace branches. The partition is therefore a no-op on the API side, and the effective rule reduces to "alphanumeric by label". It is kept rather than deleted because it is still the rule the authored side needs, and because a future TypeDoc layout could reintroduce a mixed level.

[^kind-label-map]: A derived rule — "a directory with no `index.md` is a kind directory" — would also work today, but it couples two unrelated facts and would silently mislabel any future directory that legitimately lacks an index. An explicit seven-entry map is readable at the call site and, paired with the coverage test, fails loudly rather than silently when TypeDoc emits an eighth kind. The display forms match TypeDoc's own in-page headings (`## Type Aliases`), so a reader sees the same word in the tree and on the page.

[^sentinel-file]: The alternative was a fourth branch in `DocsContent.showPath` between the `apiFileFor` miss and the fetch. Routing the synthesis through file names instead means `apiFileFor` / `apiRouteFor` / `apiDirOf` all behave exactly as they would for a real page: the round-trip test covers `/api/component` like any other route, the link base directory comes out as `component` with no special case, and the session cache in `DocsContent` keys a synthesized page like any other. `DocsContent` is not modified at all.

[^keep-vitepress-theme]: Dropping `typedoc-vitepress-theme` was investigated and rejected. Emitting `typedoc-sidebar.json` is not its only job. Its option presets (`node_modules/typedoc-vitepress-theme/dist/options/presets.js`) set `entryFileName: 'index.md'` and `hidePageHeader: true`, and its `MarkdownPageEvent.END` hook rewrites every relative link's `#anchor` through a VitePress slugifier. `entryFileName` is what produces `core/index.md` and `component/button/index.md` at all — `typedoc-plugin-markdown` defaults it to `README.md` — so removing the theme would rename all 24 index files and break `apiFileFor`, `buildApiNav`, `MODULE_INDEX_FILES` and every generated cross-link in one step. `docsRoot` is read only by the theme, to compute the sidebar JSON's link prefix. `typedoc-sidebar.json` keeps being written and keeps being excluded from the `dist/api/` copy; it is simply no longer read by the app.

[^stack-list]: That list's six bullets restate the `Proxy → Store → UI` diagram immediately above them in the order data flows: `Model` defines the shape, `Proxy` transports, `Store` orchestrates, `ModelRecord` is a row, `Association` and `Binding` build on those. Alphabetising it would open with `Association`, which depends on three concepts the reader has not met. It is prose in list form, not an index of pages, and the request was to sort link lists.
